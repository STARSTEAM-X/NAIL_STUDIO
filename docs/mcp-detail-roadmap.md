# ทำให้ MCP ออกแบบลายเล็บได้ละเอียดขึ้น — แนวทางและลำดับงาน

> สถานะ: ข้อเสนอ (ยังไม่ได้ลงมือ) — เขียนเมื่อ 2026-10-17 หลังเทียบ preset หรูกับรูปอ้างอิง 5 รูป
> ปรับครั้งที่ 2 (2026-10-17): เพิ่มผลวัดความบิดของโมเดลเล็บ (ระยะ 0), ข้อจำกัดเรื่องรูปอ้างอิง,
> tool ที่ยังขาด (1.7–1.11) และเกณฑ์วัดผล

## สรุปสั้น

ตอนนี้ MCP **ทำงานละเอียดไม่ได้ด้วย 3 เหตุผล** โดยเรียงจากผลกระทบมากไปน้อย:

1. **AI มองไม่เห็นผลงานที่ตัวเองทำจริง** — `render_preview` เป็นภาพแบน 512px
   ช่องละ 200px ตัดขอบด้วย convex hull (ไม่ใช่ทรงอัลมอนด์จริง) ไม่มีแสง ไม่มีผิว
   (มุก/ตาแมว/โครม) และของตกแต่งเป็นวงกลมพร้อมป้าย พอดูไม่ออก AI ก็ปรับให้เหมือนรูปไม่ได้
2. **ชุดคำสั่งที่ใช้วาดมีแค่สองระดับที่ห่างกันมาก** — คือ recipe ลายสำเร็จรูป (หยาบ)
   กับ `add_strokes` ดิบ (ต้องกำหนดขนาดเป็นพิกเซลและได้ครั้งละไม่เกิน 500 เส้น) ไม่มีระดับกลาง
   อย่าง path เวกเตอร์ การ์ดของการวาดเฉพาะพื้นที่ (clip) หรือการปรับลายเดิมทีละชิ้น
3. **ระบบเรนเดอร์มีเพดาน** — ทุกอย่างต้องประกอบจาก dab ของแปรงกลม จำกัด 6 เลเยอร์ × 500 stroke
   ใช้วัสดุเดียวทั้งเล็บ (ฟอยล์ทองจึงไม่เป็นโลหะจริง) และไม่มีภาพบิตแมป/เท็กซ์เจอร์

นอกจากนี้ยังมี **เหตุที่ 4 ซึ่งอยู่ใต้ทุกข้อ**: โมเดลเล็บบิดลายเองเมื่อเปลี่ยนทรงหรือความยาว
(ยืดแนวยาวได้ถึง 4 เท่าที่ปลายเล็บ ดูระยะ 0) ต่อให้ AI วาดถูกตำแหน่งใน UV ลายบนโมเดลก็ยังเพี้ยน

ทางแก้แบ่งเป็น 4 ระยะ ระยะ 0 แก้โมเดลและการ map UV ระยะ 1 แก้เฉพาะ `apps/mcp` และ `packages/patterns`
ระยะ 2–3 ต้องแก้ contracts, rasterizer ฝั่งเว็บ และ API ด้วย

## ข้อค้นพบเพิ่มเติม (จากการอ่านโค้ดและวัดโมเดล)

### ก. AI ส่งรูปที่ผู้ใช้แนบในแชตเข้า tool ไม่ได้
โมเดลภาษา "เห็น" รูปที่แนบในแชต แต่สร้าง byte ของรูปนั้นเป็น base64 เพื่อส่งเข้า tool ไม่ได้
tool ที่รับรูปอ้างอิง (1.2, 3.2, 3.3) จึงใช้ได้จริงแค่สองทาง
- **ให้ AI เทียบเอง**: tool คืนภาพ preview ที่สมจริง แล้ว AI วางเทียบกับรูปในแชตด้วยสายตาของตัวเอง
  ทางนี้ไม่ต้องทำอะไรเพิ่มนอกจาก 1.1 และควรเป็นทางหลัก
- **อัปโหลดผ่านเว็บ**: ผู้ใช้อัปโหลดรูปในเว็บ ได้ `assetId` แล้ว tool รับ `assetId`
  ห้ามรับ URL ที่ผู้ใช้หรือเนื้อหาภายนอกใส่มาให้ server ไปดึงเอง (เสี่ยง SSRF)
  ใช้โครงอัปโหลดเดียวกับ 3.2

### ข. สีใน preview ไม่ผ่านแสงแบบเดียวกับฉาก 3D
คู่มือเตือนว่าแสงใน editor ทำให้สีอ่อนลง (นู้ดต้องใช้ `#dfaaa2` แทน `#f1d4cf`) แต่ `render_preview`
แสดง hex ตรงตัว AI จึงตัดสินสีจากภาพที่ไม่ตรงกับที่ผู้ใช้เห็น ต้องแก้ใน 1.1

### ค. โมเดลเล็บบิดลายตามทรงและความยาว
ดูผลวัดและทางแก้ในระยะ 0

## ระยะ 0 — แก้โมเดลเล็บที่บิดเบี้ยว

### 0.1 ผลวัด
วัดจาก `apps/web/public/models/hand.glb` (2026-10-17) โดยหา Jacobian ของการ map UV → 3D
ต่อสามเหลี่ยม ค่า **u/v** คือ "ความยาวจริงต่อ 1 หน่วย u" หารด้วย "ความยาวจริงต่อ 1 หน่วย v"
- 1.00 = วงกลมใน UV ออกมาเป็นวงกลมบนเล็บ
- 0.50 = ถูกยืดตามแนวยาวเล็บ 2 เท่า
- 2.00 = ถูกบีบตามแนวยาว 2 เท่า

แบ่งเล็บเป็น 5 ช่วงเท่ากันตามแนว v (ตัวเลขจากนิ้วชี้ นิ้วอื่นต่างกันไม่เกินราว ±0.1):

| ทรง + ความยาว | ปลาย | 2 | 3 | 4 | โคน |
|---|---|---|---|---|---|
| round + medium (ฐาน) | 0.94 | 1.04 | 1.04 | 1.04 | 1.01 |
| square | 0.98 | 1.00 | 1.03 | 1.04 | 1.01 |
| almond | 0.57 | 0.85 | 1.01 | 1.04 | 1.01 |
| stiletto | 0.47 | 0.68 | 0.96 | 1.04 | 1.01 |
| long | 0.54 | 0.70 | 0.94 | 1.04 | 1.01 |
| extra | 0.38 | 0.53 | 0.86 | 1.04 | 1.01 |
| stiletto + extra | **0.24** | 0.39 | 0.80 | 1.04 | 1.01 |
| short | **1.96** | 1.74 | 1.15 | 1.04 | 1.01 |

สรุปจากตาราง:
1. **ทรงฐานแทบไม่บิด** (u/v เฉลี่ย 1.02–1.05) ปัญหาจึงไม่ได้อยู่ที่การกาง UV โดยรวม
2. **การยืดกระจุกอยู่ที่ปลายเล็บ** เพราะ morph ดัดเฉพาะช่วงหลัง `TAPER_START = 0.45` (DECISION D-27)
   แต่ UV ของจุดยอดไม่ขยับตาม ช่วงโคน 40% จึงไม่เปลี่ยน ส่วนช่วงปลายถูกยืดหรือบีบ
   - stiletto + extra: วงกลมที่ปลายกลายเป็นวงรีสูงราว 4 เท่า
   - short: วงกลมที่ปลายถูกบีบเหลือครึ่งเดียว
   - ลายเดียวกันจึงหน้าตาต่างกันมากในแต่ละทรง และเส้นที่ควรห่างเท่ากัน (ลายทาง, polka) จะห่างไม่เท่ากัน
3. **ขอบเล็บมีสามเหลี่ยมเรียวผิดรูป** อยู่แล้วในทรงฐาน ความบิดสูงสุด: thumb 25.5, little 5.4,
   middle 3.3 ทั้งหมดอยู่ใกล้ปลาย (v 0.07–0.15) ทำให้ลายเลอะเป็นริ้วที่ขอบปลาย
   D-27 บันทึกเรื่องนี้ไว้แล้วว่าเป็นข้อจำกัดที่รู้อยู่ แต่ยังไม่ได้แก้
4. **โค้ดฝั่งไหนรับผลนี้**
   - แผงวาด 2D ใน editor (`nailFlatten.ts`) map ผ่านสามเหลี่ยมที่ morph แล้ว ตำแหน่งที่ผู้ใช้วาดเองจึงถูกต้อง
     เหลือแค่หัวแปรงที่บิดเป็นวงรี
   - **ลายจาก recipe/preset และ stroke ที่ AI ส่งมาเขียนลง UV ตรง ๆ จึงโดนการยืดเต็มที่**
     AI และ MCP จึงได้รับผลหนักที่สุด

### 0.2 ทางแก้
หลักการคือ **ให้ตำแหน่งยังเป็นสัดส่วนของเล็บ แต่ระยะห่างตามแนวยาวต้องเท่ากันจริง**
v = 0 ยังเป็นปลาย และ v = 1 ยังเป็นโคนเสมอ (French, ไล่สี และ preset เดิมยังวางตรงที่เดิมโดยสัดส่วน)
แต่ v ที่ห่างกันเท่ากันต้องห่างกันเท่ากันบนผิวจริงด้วย

**0.2.1 UV morph target (แก้ที่ต้นเหตุ)**
- `tools/build_model.py` / `nail_geometry.py`: สำหรับ target แต่ละตัว ให้วัดความยาวผิวสะสมตามแกน
  PCA จากปลายถึงโคนบนเมช morph แล้ว หาฟังก์ชัน `F(v)` ที่ทำให้ความยาวต่อหน่วย v คงที่
  แล้วเก็บ delta `(0, F(v) − v)` ของทุกจุดยอดเป็น attribute ต่อ target (เช่น `_UV_ALMOND`)
  - ทิศ u ไม่แก้ เพราะทรงเรียวต้องบีบความกว้างเข้าหาปลายอยู่แล้ว (ลายวิ่งตามขอบเล็บ)
  - delta ต่อ target บวกกันได้เหมือน position จึงยังผสมทรงกับความยาวได้แบบเดิม
    แต่ต้องวัดซ้ำทุกคู่ผสม (5 ทรง × 4 ความยาว = 20 คู่)
- three.js ไม่ morph UV ให้เอง จึงต้องทำสองที่
  - ฝั่ง GPU: แทรกการบวก delta ใน vertex shader ด้วย `onBeforeCompile` ของวัสดุเล็บ
    ใช้ค่าน้ำหนักชุดเดียวกับที่ `applyNailMorphs` ตั้ง
  - ฝั่ง CPU: เพิ่ม `morphedUv()` ใน `nailMorph.ts` คู่กับ `morphedPosition`
    แล้วให้ `nailFlatten.ts`, `surfaceProjection.ts` (วางของตกแต่ง) และ preview ของ MCP ใช้ตัวนี้
- ข้อดี: texture ไม่ขึ้นกับทรง ไม่ต้องวาดใหม่ตอนเปลี่ยนทรง และ rasterizer ไม่ต้องแก้

**0.2.2 กาง UV ทรงฐานใหม่**
เปลี่ยนจากการฉายตามแกน PCA เป็น LSCM/ABF ตามที่ D-27 ประเมินไว้
เพื่อกำจัดสามเหลี่ยมเรียวที่ขอบปลาย ทำในรอบเดียวกับ 0.2.1 เพราะต้อง build `hand.glb` ใหม่อยู่แล้ว

**0.2.3 ชดเชยรูปร่างเฉพาะจุด (ทำหลัง 0.2.1 และ 1.3)**
หลัง 0.2.1 การยืดจะสม่ำเสมอทั้งเล็บ เหลือเป็นค่าคงที่ k ต่อทรง
(ประมาณ long 1.23, extra 1.49, short 0.79 เทียบกับทรงฐาน) วงกลมยังเป็นวงรีอ่อน ๆ อยู่
- `packages/patterns`: ลายที่เป็นชิ้น (จุด หัวใจ ดอกไม้ ผีเสื้อ ตัวอักษร) สร้างรูปร่างรอบจุดยึดโดยหารแนว v ด้วย k
  ของทรงนั้น (`buildFromRecipe` รู้ทรงและความยาวอยู่แล้ว)
  ส่วนลายที่เป็นพื้น (ไล่สี French หินอ่อน) ไม่ต้องชดเชย
- พอมี `source` จาก 1.3 แล้ว `set_nail_properties` ต้องสร้างลายชิ้นใหม่ตาม k ของทรงใหม่
- หัวแปรงจากการวาดเองบนแผง: ให้ rasterizer วาด dab เป็นวงรีตาม k
  (ต้องส่งทรงเข้า `renderLayer` และวาด texture ใหม่ตอนเปลี่ยนทรง) จะทำหรือไม่ให้ตัดสินหลังเห็นผล 0.2.1

### 0.3 ผลต่องานเดิมและเกณฑ์ผ่าน
- **ผลต่องานที่บันทึกไว้**: ถ้าเปลี่ยนการ map ให้ทุกงาน งานที่ใช้ทรงหรือความยาวอื่นนอกจาก round/medium
  ลายช่วงปลายจะขยับตำแหน่งบนผิวจริง
  **ตัดสินแล้ว (2026-10-17): งานเก่าต้องคงหน้าตาเดิม** ใช้ฟิลด์ `uvMapping` ต่อเอกสาร ดู 0.4
- **เกณฑ์ผ่าน** (ให้ `verify_model.py` ตรวจ ทุกนิ้ว × 20 คู่ทรง/ความยาว)
  - ความสม่ำเสมอ: (u/v สูงสุดของช่วง) ÷ (u/v ต่ำสุดของช่วง) ≤ 1.2 ยกเว้นช่วงปลายของ almond/stiletto
    ที่ u ถูกบีบตามทรง (ปัจจุบัน extra = 2.7, stiletto + extra = 4.3)
  - ทรงฐาน: ความบิดเฉลี่ยถ่วงพื้นที่ ≤ 1.10 และเปอร์เซ็นไทล์ที่ 99 ≤ 1.5
    (แทน `MAX_UV_DISTORTION` ที่ตรวจค่าสูงสุดตัวเดียว ซึ่งโดนสามเหลี่ยมชิ้นเดียวทำให้ไม่ผ่านได้ง่าย)
  - ภาพทดสอบ: วาดตาราง polka และ checker ลงทุกทรงแล้วถ่ายจากมุมหน้าเล็บ จุดต้องกลมและช่องต้องเท่ากันด้วยตาเปล่า
- สคริปต์วัดที่ใช้ทำตารางใน 0.1 ควรเก็บเป็น `tools/measure-uv-distortion.mjs`
  (อ่าน GLB รวม morph target แบบ sparse แล้วรายงานรายช่วง)

### 0.4 ฟิลด์ `uvMapping` — ให้งานเก่าคงหน้าตาเดิม
**ค่า**: `uvMapping: 'legacy' | 'arc-length'` ที่ระดับเอกสาร (ไม่ใช่ต่อเล็บ เพราะทุกนิ้วใช้โมเดลชุดเดียวกัน)
- `legacy` = ไม่บวก UV delta ใดเลย ได้ผลเหมือนปัจจุบันทุกพิกเซล รวมถึงการยืดที่ปลายเล็บ
- `arc-length` = ใช้ UV morph จาก 0.2.1

**ทำไม bump เป็น schema v4 แทนการเพิ่มฟิลด์ optional**
- schema ใน `packages/contracts/src/design.ts` เป็น `z.object` ปกติ ซึ่ง**ตัดคีย์ที่ไม่รู้จักทิ้ง**ตอน parse
  ถ้าเป็นฟิลด์ optional แล้วให้ "ไม่มีค่า = legacy" แท็บเว็บรุ่นเก่าที่ยังเปิดค้างอยู่ตอน deploy
  จะ parse งานใหม่ ตัดฟิลด์ทิ้ง แล้วบันทึกกลับ งานจะเปลี่ยนเป็น legacy เงียบ ๆ โดยไม่มีใครรู้
- ถ้า bump เป็น v4 แล้ว client รุ่นเก่า (`z.literal(3)`) จะ parse งาน v4 ไม่ผ่าน
  ผลคือ error ให้เห็น ไม่ใช่ข้อมูลเพี้ยนเงียบ ๆ
- โปรเจกต์มีนโยบาย migrate ตอนอ่านอยู่แล้ว (`migrateDesignDocument`, database.md §5) เอกสารเก็บเป็น jsonb
  **จึงไม่ต้องย้ายข้อมูลในฐานข้อมูล**

**การ migrate และค่าเริ่มต้น**
| กรณี | ค่าที่ได้ |
|---|---|
| เอกสาร v2 / v3 ทุกฉบับ (งานเก่า, เวอร์ชันเก่า, template เก่า) | migrate เป็น v4 + `legacy` |
| `createEmptyDocument()` (งานใหม่จากเว็บหรือ `create_project` ของ MCP) | `arc-length` |
| remix จาก template | ใช้ค่าของ template ต้นทาง (template เก่าได้ `legacy` หน้าตาจึงตรงกับต้นฉบับ) |
| `revert_to_version` (1.8) | ใช้ค่าของเวอร์ชันที่ย้อนไป |

- migration ต้องต่อกันเป็นทอด v2 → v3 → v4 ใน `migrateDesignDocument` (ตอนนี้รองรับแค่ v2 → v3)
- ต้องเพิ่มเทสต์ migration และอัปเดตเทสต์ที่ตรวจ `schemaVersion` (เช่น `slice1.integration.test.ts`)

**จุดที่ต้องอ่านค่านี้** (ทั้ง 4 จุดของการ map UV ต้องได้ค่าเดียวกันเสมอ)
1. shader ของวัสดุเล็บ: ส่ง uniform `uvMorphScale` เป็น 0 (legacy) หรือ 1 (arc-length) ไปคูณกับ UV delta
2. `nailMorph.ts` → `morphedUv(mesh, mode)` ที่ `nailFlatten.ts` และ `surfaceProjection.ts` ใช้
3. preview ของ MCP (`render.ts`)
4. `lint_design` (1.9): เตือนเรื่องลายชิ้นที่ปลายเล็บถูกยืดเฉพาะงานที่เป็น `legacy`

**การย้ายงานเก่ามาใช้แบบใหม่ (ผู้ใช้เลือกเอง)**
- เว็บ: ปุ่มใน editor settings สำหรับงาน `legacy` บอกว่าลายช่วงปลายจะขยับ และแสดงตัวอย่างก่อน/หลัง
  เมื่อกดจะบันทึกเป็นเวอร์ชันใหม่ จึงย้อนกลับได้
- MCP: tool `set_uv_mapping(projectId, mode)` ซึ่งต้องใช้ `dryRun` ได้ (1.7)
- ทางเลือกเพิ่มทีหลัง: ตอนย้าย ให้แปลงพิกัด v ของ stroke และของตกแต่งด้วยฟังก์ชันผกผันของ `F(v)`
  ตามทรงของแต่ละนิ้ว ตำแหน่งบนผิวจริงจะเหมือนเดิม และได้ระยะห่างสม่ำเสมอกับงานที่ทำต่อจากนี้
  เมื่อทรงมีแค่ 20 คู่ ความซับซ้อนจะเป็น O(จำนวนจุด) ต่อเอกสาร

**ผลข้างเคียงที่ต้องจัดการ**

  ต้องตรวจซ้ำในโหมด `arc-length` ด้วย `tools/pattern-review.html` (เพิ่มตัวเลือกสลับโหมด)
- ควรทำ 1.3 (ฟิลด์ `source` ใน layer) พร้อมกับ v4 ในรอบเดียว จะได้ bump schema ครั้งเดียว

  ผู้ใช้จะเปิดงานใหม่ไม่ได้)

## ระยะ 1 — ให้ AI เห็นชัดและแก้ได้ทีละจุด (แก้แค่ MCP + patterns)

### 1.1 `render_preview` ความละเอียดสูงและเหมือนจริงขึ้น
- เพิ่มพารามิเตอร์ `zoom: 'hand' | 'nail'` และ `resolution: 512 | 1024`
  ถ้าเป็น `nail` ให้เรนเดอร์นิ้วเดียวเต็มภาพ 1024 จะเห็นรายละเอียดเกล็ดฟอยล์/เส้นบาง
- แสดง**ทรงเล็บจริงตาม `shape` และ `length`** แทน convex hull โดยใช้วิธีเดียวกับ `nailFlatten.ts`
  ของแผงวาดใน editor: ใส่ morph ให้จุดยอด ฉายลงระนาบหน้าเล็บ แล้ววาด texture ทีละสามเหลี่ยม
  ได้ทั้งขอบทรงจริง**และการยืดของลายแบบเดียวกับที่โมเดลทำ** (ระยะ 0) ในขั้นเดียว
  - `render.ts` อ่าน accessor ของ GLB อยู่แล้ว เพิ่มแค่การอ่าน POSITION และ morph target แบบ sparse
  - ต้องได้ผลตรงกับแผงวาด ควรแยกส่วนคำนวณที่ไม่พึ่ง three ออกมาใช้ร่วมกัน แทนการเขียนสูตรใหม่
- **ปรับสีให้ตรงกับฉาก**: ผ่าน tone mapping และ exposure ค่าเดียวกับ `NailScene` (และ sRGB เหมือนกัน)
  ก่อนส่งภาพ ให้สีที่ AI เห็นใกล้กับที่ผู้ใช้เห็นบนโมเดล (ดูข้อค้นพบ ข)
- จำลองผิวแบบ 2.5D ราคาถูก: เงาขอบ (vignette ตามความโค้งเล็บ) + แถบไฮไลต์เงา 1 เส้น
  + ผลของ finish (ตาแมว = แถบสว่างตามมุม, มุก = เหลือบรุ้งบาง, โครม = ไล่เงาโลหะ)
- วาดของตกแต่งเป็น sprite มีแสงเงาตามชนิด (เพชรเหลี่ยม/มุก/โลหะ) แทนวงกลม และใช้ขนาดตามสเกลจริง
- **ผลที่ได้:** AI เทียบกับรูปอ้างอิงได้ด้วยตัวเอง และวน preview → ปรับ ได้มีความหมาย

### 1.2 `compare_preview` — วางเทียบกับรูปอ้างอิง
> ⚠️ ทำหลังมีระบบอัปโหลดรูปเท่านั้น (ข้อค้นพบ ก) ระหว่างนี้ให้ AI เทียบภาพจาก 1.1 กับรูปในแชตเอง
- รับรูปอ้างอิงเป็น `assetId` จากการอัปโหลดในเว็บ (ไม่รับ URL ภายนอก) แล้วคืนภาพวางคู่กันกับ preview
- คืนตัวเลขช่วยตัดสินใจไปด้วย ได้แก่ palette หลัก 6 สีของแต่ละฝั่ง (k-means)
  และระยะสี ΔE เฉลี่ยของสีพื้น/สีลาย
- ไม่ต้องแม่นระดับ CV แค่บอกได้ว่า "สีพื้นอ่อนไป" หรือ "ทองน้อยไป" ก็ช่วยมากแล้ว

### 1.3 เก็บ "ที่มาของลาย" ไว้ในเอกสาร แล้วแก้ทีละลายได้
ตอนนี้ recipe ถูกแปลงเป็น stroke ทันทีและไม่เก็บพารามิเตอร์ไว้ ถ้าจะปรับลายต้องสร้างใหม่ทั้งนิ้ว
- เก็บ `source: { type, params }` ไว้ที่ layer (หรือแยกเป็นฟิลด์ `patterns` ข้างเล็บ) ให้รู้ว่า
  layer นี้มาจากลายอะไร
- เพิ่ม tool `list_layers`, `update_pattern(nail, index, patch)`, `remove_pattern`, `move_pattern`
  ซึ่งจะสร้าง stroke ใหม่เฉพาะลายนั้น
- **ผลที่ได้:** AI ปรับได้ทีละจุด เช่น "ขยับผีเสื้อลง 0.05" หรือ "เพิ่มเกล็ดทอง" โดยไม่ทำลายส่วนอื่น

> หมายเหตุ: 1.3 ต้องเพิ่มฟิลด์แบบ optional ใน `layerSchema` ซึ่งเข้ากันได้กับเอกสารเดิม
> ถ้าทำแยกก็ไม่ต้อง bump schema version แต่ client รุ่นเก่าจะตัด `source` ทิ้งตอนบันทึกได้
> (ไม่ร้ายแรง แค่เสียข้อมูลสำหรับแก้ทีละลาย) ถ้าทำพร้อมกับ 0.4 ให้ใส่ใน v4 ไปเลย

### 1.4 การแปลงลายแบบใช้ได้กับทุกลาย (transform / repeat / clip)
เพิ่มฟิลด์กลางให้ทุก pattern ใน recipe (ห่อชั้นนอก ไม่แตะ renderer ทีละตัว):
- `transform: { offset:[du,dv], scale, rotate, mirror }` — ย้าย/หมุน/ย่อลายสำเร็จรูปได้ทุกตัว
- `repeat: { along: points | grid, count }` — เรียงซ้ำ เช่น ดาวเรียงตามเส้นโค้ง
- `clip: 'tip' | 'body' | { polygon }` — ตัด stroke ให้อยู่ในพื้นที่ เช่น ให้กลิตเตอร์อยู่เฉพาะในปลาย
  French (ตัดที่ระดับจุดของ stroke ทำได้ในฝั่ง patterns ไม่ต้องแก้ rasterizer)
- `opacity` / `blend` ต่อลาย (map ไปที่ layer)

### 1.5 `add_path` — วาดจาก SVG path
LLM เขียน SVG path ได้ดีกว่าการกะพิกัด dab ทีละจุดมาก
- รับ `d` (SVG path data ในพิกัด UV 0–1), `fill`, `stroke`, `strokeWidth` (หน่วย UV), `opacity`
- ฝั่ง server flatten เส้นโค้งเป็น polygon แล้วใช้ `fill()` และ `line()` เดิม ทำให้ได้ขอบเนียนจาก
  งานแก้ขั้นบันไดที่ทำไปแล้ว
- ทำให้วาดลายที่ไม่มีใน catalog ได้ละเอียด เช่น ลูกไม้ ตัวอักษร โลโก้ หรือดอกไม้ที่ออกแบบเอง

### 1.6 เพิ่มคู่มือและตัวอย่างใน resource
- `nailstudio://guide` เพิ่มสูตรการซ้อนชั้นตามประเภทงาน (หินอ่อน, ฟอยล์, ออร่า, French หรู)
  พร้อมภาพตัวอย่าง (embed เป็น resource รูป)
- prompt `design_from_reference`: ขั้นตอนแยกรูป → palette → ร่างต่อนิ้ว → preview 1024 →
  compare → ปรับ ≥ 2 รอบ → apply

### 1.7 `dryRun` ทุก tool ที่บันทึก และคืนภาพหลังบันทึก
ตอนนี้มีแค่ `preview_recipe` ที่ดูผลก่อนบันทึกได้ ส่วน `add_strokes`, `add_decoration`, `set_nail`,
`set_nail_properties`, `copy_nail` และ `clear_nail` บันทึกทันที
- เพิ่ม `dryRun: boolean` ให้ทุกตัว ทำได้ที่ `updateDesign` จุดเดียว: ถ้า dryRun ให้คืนภาพโดยไม่เรียก `saveVersion`
- ทุกครั้งที่บันทึกสำเร็จให้คืนภาพเฉพาะนิ้วที่เปลี่ยน (ปิดได้ด้วย `preview: false`)
  จะลดการเรียก `render_preview` ซ้ำไปครึ่งหนึ่ง

### 1.8 `list_versions` / `revert_to_version`
API มี `GET /projects/:id/versions` และ `GET /projects/:id/versions/:version` อยู่แล้ว
(`apps/api/src/projects/routes.ts`) เพิ่มแค่เมธอดใน `apiClient.ts` และ tool สองตัว
- `revert_to_version` = อ่านเวอร์ชันเก่าแล้วบันทึกเป็นเวอร์ชันใหม่ (ไม่ลบประวัติ) ส่ง `expectedVersion` เหมือนเดิม
- ทำให้ AI กล้าลองปรับ เพราะถ้าแย่ลงก็ถอยเองได้

### 1.9 `lint_design` — ตรวจกฎในคู่มืออัตโนมัติ
ตอนนี้กฎใน `DESIGN_RULES` เป็นแค่ข้อความ ให้ตรวจเป็นโค้ดใน `packages/patterns` แล้วคืนคำเตือนพร้อมทุก preview
- stroke หรือของตกแต่งอยู่นอกพื้นที่ที่มองเห็น (u 0.2–0.8, v 0.05–0.95)
- สีลายกับสีที่อยู่ข้างใต้ต่างกันน้อยเกิน (ΔE ต่ำกว่าเกณฑ์) = มองไม่เห็น
- จำนวนเลเยอร์/stroke เกิน 80% ของเพดาน
- ลายหนาแน่นเกิน 2 ลายต่อเล็บ
- ลายชิ้นวางในช่วงปลายของทรงที่ยืดมาก (จนกว่าระยะ 0 จะเสร็จ)
- ความซับซ้อน O(จำนวน stroke + จำนวนของตกแต่ง) ต่อเล็บ

### 1.10 `describe_pattern(type)`
`list_patterns` บอกให้ไปอ่านพารามิเตอร์จาก JSON Schema ของ `apply_recipe` ซึ่งใหญ่มากเมื่อมี 41 ลาย
ให้คืนพารามิเตอร์ ค่าเริ่มต้น ช่วงค่า และภาพย่อของลายนั้นลายเดียว

### 1.11 `preview_variants`
รับ recipe หลายชุด (หรือชุดเดียวกับ seed หลายค่า) แล้วคืนภาพรวมแผ่นเดียว
ให้ AI หรือผู้ใช้เลือกแบบ แทนการลองทีละรอบ จำกัดไม่เกิน 6 แบบต่อครั้ง เพื่อคุมเวลาและขนาดภาพ

## ระยะ 2 — เพิ่มความสามารถของระบบวาด (แก้ contracts + rasterizer เว็บ + MCP)

### 2.1 stroke ชนิดใหม่ที่แสดงผลได้เนียนกว่าและใช้จำนวนน้อยกว่า
ตอนนี้การไล่สีหนึ่งครั้งใช้ airbrush ซ้อนกัน 15–30 เส้น ออร่าใช้ 37 จุด
- `kind: 'shape'` — polygon/path พร้อม fill แบบ solid, `linear` หรือ `radial` gradient
  และ feather ที่ขอบ ทำให้ไล่สีเนียนเป็นพิกเซล ไม่มีแถบ และขอบคมด้วย anti-alias จริง
- `kind: 'procedural'` — ให้ rasterizer สร้างเท็กซ์เจอร์จาก `{ kind: 'marble'|'malachite'|'glitter'|'cat_eye'|'noise', seed, params }`
  ด้วย noise ระดับพิกเซล (fbm + domain warp) ทำให้หินอ่อนและควันดูเป็นธรรมชาติแบบที่ stroke ทำไม่ได้
  และเอกสารเล็กลงมาก (จากพัน stroke เหลือ 1 รายการ)
- ต้อง implement ใน `apps/web/src/3d/painting/rasterizer.ts` ซึ่ง MCP ใช้ตัวเดียวกันอยู่แล้ว
  ภาพ preview จึงตรงกับเว็บอัตโนมัติ

### 2.2 วัสดุแยกตามพื้นที่ (material mask)
ตอนนี้ `finish` ใช้กับทั้งเล็บ ฟอยล์ทองจึงเป็นแค่สีเหลืองบนเจลเงา
- เพิ่ม `material` ต่อ layer: `'paint' | 'metal' | 'chrome' | 'glitter' | 'pearl'`
- rasterizer สร้าง roughness/metalness map ขนาดเดียวกับ color map แล้ว `MeshPhysicalMaterial`
  ใช้ `roughnessMap` และ `metalnessMap`
- ผลคือเส้นทอง/ฟอยล์สะท้อนแสงเป็นโลหะจริงตอนหมุนมือ และกลิตเตอร์วิบวับเฉพาะจุด
  ซึ่งเป็นตัวที่ทำให้งานดูหรูมากที่สุดในรูปอ้างอิง 1, 2 และ 5
- ต้นทุน: texture เพิ่ม 1 ใบต่อเล็บ (ต้องคิดหน่วยความจำบนมือถือตาม `NailTextureSet.ts`)

### 2.3 ขยายเพดาน
- texture 2048 สำหรับโหมด "รายละเอียดสูง" บนเดสก์ท็อปเท่านั้น (มือถือคง 1024
  ดู `docs/tasks/mobile-paint-perf.md`)
- เพิ่ม `MAX_STROKES_PER_LAYER` หรือจำนวนเลเยอร์เฉพาะ layer ที่สร้างจากลาย แต่เมื่อมี 2.1 แล้ว
  แทบไม่ต้องเพิ่ม เพราะ procedural ลดจำนวน stroke ลงมาก
- ⚠️ `size` ของ stroke เป็นพิกเซลบน texture 1024 (`render.ts` ย่อด้วย `TEX / EDITOR_TEX`)
  texture 2048 จึงต้องคูณขนาดตามอัตราส่วนเดียวกัน ไม่อย่างนั้นทุกเส้นจะบางลงครึ่งหนึ่ง
  ทางที่ดีกว่าคือให้ `shape` ใน 2.1 ใช้หน่วย UV ตั้งแต่แรก

### 2.4 ของตกแต่ง 3D ที่สมจริง
- วัสดุเพชร: `MeshPhysicalMaterial` ตั้ง `transmission`, `ior 2.4`, `dispersion` และ env map
  ความละเอียดสูง พร้อมเรขาคณิตเจียระไน (brilliant / marquise / pear)
- โหลด GLB จริงผ่าน `modelUrl` ที่เตรียมช่องไว้แล้วใน `decorationCatalog.ts`
- `add_decoration_path`: วางของตามเส้นโค้งอัตโนมัติ เช่น สายลูกปัดหรือแถวเพชรไล่ขนาด

## ระยะ 3 — ใกล้เคียงรูปถ่ายที่สุด

### 3.1 `render_3d` — เรนเดอร์ฉากจริงจากเซิร์ฟเวอร์
- ใช้ headless Chromium (Playwright) เปิดหน้า viewer ภายในที่ใช้ `NailScene` ตัวเดียวกับเว็บ
  ส่งเอกสารเข้าไป แล้วถ่ายภาพตามมุมกล้องที่ขอ (`angle`, `focus: nail key`, ทิศแสง)
- ให้ AI เห็นผลของ finish, ของตกแต่ง และทรงเล็บแบบเดียวกับผู้ใช้ทุกอย่าง
- ต้นทุน: ใช้ RAM ประมาณ 300–500 MB ต่อ instance และใช้เวลา 1–3 วินาทีต่อภาพ
  service ฟรีบน Render รับไม่ไหว ต้องรันเป็น worker แยก หรือรันเฉพาะตอน dev
- ทางที่ถูกกว่า: `headless-gl` + three ใน Node ใช้ได้กับ shader ส่วนใหญ่ แต่เชื่อถือได้น้อยกว่า

### 3.2 ชั้นภาพบิตแมป (decal / image layer)
นี่คือทางเดียวที่จะได้เหมือนรูปถ่ายเกือบ 100% สำหรับลวดลายธรรมชาติ (หินอ่อน, ฟอยล์ยับ, ลูกไม้)
- เพิ่ม `kind: 'image'` ใน stroke/layer ที่อ้างถึง asset (เก็บที่ storage เช่น Supabase/S3)
  พร้อม transform UV
- tool `add_image_layer(nail, assetId, region)` สำหรับครอปจากรูปอ้างอิง
  หรือจากเท็กซ์เจอร์ที่ gen มา แล้ววางลงเล็บ (รับ `assetId` จากการอัปโหลดในเว็บ ดูข้อค้นพบ ก)
- ต้องมี: API อัปโหลดพร้อมตรวจชนิดไฟล์และขนาด, จำกัดขนาด (เช่น 1024² webp), ลบ asset
  ที่ไม่ถูกใช้ และ bump schema version + migration
- ข้อควรระวัง: ลิขสิทธิ์ของรูปที่ครอปมา และเอกสารจะใหญ่ขึ้น (ต้องเก็บแค่ URL ไม่ฝัง base64)

### 3.3 `trace_reference` — แปลงรูปอ้างอิงเป็นเวกเตอร์
- รับรูปเล็บหนึ่งเล็บที่ครอปแล้ว (เป็น `assetId`) → แยกสี (k-means) → vectorize แต่ละสี
  (potrace / marching squares) → ได้ `shape` stroke ในพิกัด UV
- ได้ลวดลายตรงรูปจริงโดยไม่ต้องเก็บบิตแมป จึงแก้ไขต่อได้ ปลอดภัยกว่า 3.2 แต่หยาบกว่า

## การวัดผล
ยังไม่มีเกณฑ์ว่า "ละเอียดขึ้น" แล้วจริง ควรตั้งก่อนเริ่มระยะ 1
- **ชุดทดสอบคงที่**: ใช้รูปอ้างอิง 26 รูปและ preset ที่จับคู่ไว้ใน `docs/pattern-reference-quality.md`
- **ภาพมาตรฐาน (golden image)**: `tools/render-pattern-catalog.mjs` เรนเดอร์ทุก preset แล้วเก็บไว้
  ทุกงานที่แตะ rasterizer, preview หรือโมเดลต้องเทียบกับภาพชุดนี้ และอัปเดตเมื่อการเปลี่ยนตั้งใจ
- **วัดการบิด**: `tools/measure-uv-distortion.mjs` ตามเกณฑ์ใน 0.3
- **ทดลองการใช้งานจริง**: ให้ AI ทำตามรูปอ้างอิง 5 รูปผ่าน MCP แล้วนับจำนวนรอบจนผู้ใช้ยอมรับ
  และเทียบ ΔE ของสีพื้นกับสีลายก่อนและหลังแต่ละระยะ

## ความเสี่ยงร่วม
- ทุกฟีเจอร์ที่แก้ rasterizer ต้องได้ผลเหมือนกันบนเว็บและ Node (ใช้ไฟล์เดียวกันอยู่แล้ว
  แต่ canvas ของ `@napi-rs` กับเบราว์เซอร์รองรับ gradient/filter ต่างกันเล็กน้อย)
  ต้องมี visual regression test ที่วาดชุดเดียวกันทั้งสองฝั่งแล้วเทียบความต่างของพิกเซล
  ไม่ใช่แค่ระบุไว้ในเอกสาร
- การ map UV มีอยู่ 4 จุดที่ต้องตรงกันเสมอ: shader, `nailFlatten.ts`, `surfaceProjection.ts`
  และ preview ของ MCP ถ้าแก้จุดใดจุดเดียว (เช่น ใส่ UV morph แค่ใน shader) ลายกับของตกแต่ง
  หรือแผงวาดจะเลื่อนออกจากกัน ต้องมีเทสต์ที่ตรวจว่าทั้ง 4 จุดให้ค่าเดียวกัน
- texture ใหญ่ขึ้นและ map เพิ่มขึ้นกระทบหน่วยความจำบน iPad โดยตรง ต้องวัดซ้ำทุกครั้ง
- ขนาด payload ของ MCP (base64 ภาพ 1024 ราว 0.5–1.5 MB ต่อภาพ) client บางตัวมีเพดาน
  จึงควรมีโหมด `format: 'webp'` และเลือกครอปเฉพาะนิ้ว
