# การวิเคราะห์เปรียบเทียบและออกแบบ ER ฉบับสมบูรณ์

ระบบ Nail Studio 3D — ออกแบบเล็บ 3 มิติ + ชุมชนแชร์แม่แบบ + จองร้าน + แชท + ผู้ช่วย AI

---

## 1. ขอบเขตและวิธีการ

เอกสารนี้เปรียบเทียบการออกแบบฐานข้อมูล 2 ชุดที่มีอยู่ แล้วสังเคราะห์เป็นชุดที่สาม

| ชุด | ที่มา | ขนาด | สถานะ |
|---|---|---|---|
| ก. ดีไซน์เดิม | `Olddesine/*.txt` (6 ไฟล์) | 33 ตาราง | ออกแบบไว้ก่อนเริ่มพัฒนา ยังไม่ได้สร้างจริง |
| ข. สคีมาปัจจุบัน | `prisma/schema.prisma` + migration 14 ชุด | 25 ตาราง / 14 enum | สร้างจริงแล้ว มีข้อมูลใช้งาน |
| ค. **ฉบับสมบูรณ์** | เอกสารนี้ → `00-full-system.dbml` | **39 ตาราง / 16 enum** | ข้อเสนอ |

วิธีการ: แยกเป็น 8 โดเมน แล้วในแต่ละโดเมนตัดสินทีละประเด็นด้วยเกณฑ์ข้อ 2
โดยไม่ถือว่าชุดใดชุดหนึ่งถูกต้องกว่าโดยปริยาย

## 2. เกณฑ์การตัดสิน

เรียงตามน้ำหนัก มากไปน้อย

1. **ความถูกต้องของข้อมูล** — ฐานข้อมูลบังคับกฎเองได้หรือไม่ ถ้าโค้ดพลาดแล้วข้อมูลจะเสียหรือเปล่า
2. **ความปลอดภัย** — ข้อมูลรั่วแล้วเสียหายแค่ไหน
3. **ตอบคำถามที่ระบบต้องถามได้จริง** — ทุก use case ต้องเขียนเป็น query ได้
4. **รูปแบบบรรทัดฐาน (Normal Form)** — ยกเว้นกรณีที่ตั้งใจฝ่าฝืนและอธิบายได้
5. **ประสิทธิภาพ** — จำนวน query ต่อการโหลดหนึ่งหน้า
6. **ความเรียบง่าย** — ตารางน้อยกว่าดีกว่า ถ้าไม่ขัดข้อ 1–5

### 4.1 Identity & Auth

| ประเด็น | ดีไซน์เดิม | ปัจจุบัน | เลือก | เหตุผล |
|---|---|---|---|---|
| เก็บ session | `refresh_token text` (ดิบ) | `token_hash bytea` | **ปัจจุบัน** | เก็บ token ดิบ = ฐานข้อมูลรั่วเมื่อไร ผู้โจมตีสวมสิทธิ์ได้ทุกคนทันที เก็บ hash แล้วรั่วก็ปลอมไม่ได้ |
| บทบาท | `roles` + `user_roles` (N:M) | `role` enum | **ปัจจุบัน** | ระบบมีบทบาทตายตัว 3 แบบ ไม่มีความต้องการให้แอดมินสร้างบทบาทใหม่ตอนรันไทม์ ตาราง N:M จึงเพิ่ม 2 ตารางและ 1 join ทุกครั้งที่ตรวจสิทธิ์ โดยไม่ได้อะไรกลับมา |
| ลืมรหัสผ่าน | `password_resets` | **ไม่มี** | **เดิม** | ช่องว่างจริง — ตอนนี้ผู้ใช้ลืมรหัสผ่านแล้วจบเลย |
| ประวัติเข้าสู่ระบบ | `login_history` | **ไม่มี** | **เดิม** | ใช้ตรวจจับการเดารหัสผ่านและตอบคำถาม "ใครเข้าบัญชีฉัน" ฉบับใหม่เพิ่ม `email_attempted` เพื่อบันทึกการล็อกอินที่อีเมลไม่มีในระบบด้วย |
| `username` | ✓ | ✗ | **เดิม** | ชุมชนต้องมีชื่อเฉพาะสำหรับ URL โปรไฟล์และการ mention — `display_name` ซ้ำกันได้ ใช้แทนไม่ได้ |
| `is_active` / ระงับบัญชี | `is_active` | ✗ | **เดิม + ขยาย** | ปัจจุบันมีระบบรับรายงานแต่ **ไม่มีทางลงโทษ** เพิ่ม `is_active` (ถาวร) และ `suspended_until` (ชั่วคราว) |
| รูปโปรไฟล์ | ✗ | ✗ | **เพิ่มใหม่** | หน้าเว็บใช้ `avatarGradient` สุ่มสีแทนรูปจริง เพราะฐานข้อมูลไม่มีที่เก็บ |

|---|---|---|---|---|
| ที่เก็บงานออกแบบ | `nail_templates.nail_layers` | `projects` → `design_versions` → `nail_templates` | **ปัจจุบัน** | **จุดชี้ขาดของทั้งการเปรียบเทียบ** ดีไซน์เดิมใช้ตารางเดียวเป็นทั้งงานส่วนตัวและโพสต์สาธารณะ ผลคือ "เลิกเผยแพร่" กับ "ลบงานตัวเอง" เป็นการกระทำเดียวกัน และ autosave จะเขียนทับสิ่งที่คนอื่นกำลังดูอยู่ |
| เวอร์ชัน | `template_versions(template_id, version_no)` unique | `design_versions(project_id, version_number)` unique | **ปัจจุบัน** | เวอร์ชันควรผูกกับ *งาน* ไม่ใช่ *โพสต์* — งานหนึ่งเผยแพร่ได้หลายโพสต์ และแก้ต่อได้แม้ลบโพสต์ไปแล้ว |
| autosave | ไม่มีแนวคิดนี้ | `draft_document` + `draft_base_version` | **ปัจจุบัน** | ถ้าให้ autosave สร้างเวอร์ชันทุก 3 วินาที นั่งวาด 1 ชั่วโมงจะได้ 1,200 เวอร์ชัน จนหาเวอร์ชันที่ต้องการไม่เจอ |
| ที่อยู่ไฟล์ | `file_url text` | `storage_key` + `mime_type` + `size_bytes` + `checksum` | **ปัจจุบัน** | `checksum` ทำให้อัปไฟล์เดิมซ้ำใช้แถวเดิมได้ และ `storage_key` ทำให้ย้าย CDN โดยไม่ต้อง UPDATE ทุกแถว |
| ขนาดภาพ | คอลัมน์ `width` / `height` | ซ่อนใน `metadata jsonb` | **เดิม** | ต้องตรวจขนาดทุกครั้งที่อัปโหลด การอ่านจาก jsonb ทุกครั้งทั้งช้ากว่าและตั้ง CHECK constraint ไม่ได้ |

### 4.3 Community

| ลิงก์แชร์ | `share_code` + `expires_at` + `allow_copy` + counter | log ช่องทางที่กดแชร์ | **รับทั้งคู่** | คนละเรื่องกัน — ลิงก์คือ *ทรัพยากร* (คนไม่มีบัญชีเปิดดูได้) log คือ *พฤติกรรม* (ไว้ทำสถิติ) ฉบับใหม่มีทั้ง `template_share_links` และ `template_share_events` |

| ระดับความยาก | `difficulty smallint` | ✗ | **เดิม** | เป็นตัวกรองที่ผู้ใช้มือใหม่ต้องการจริง และของปัจจุบันทำหล่นหายไป |

### 4.4 Moderation & Notification

### 4.5 Shop & Booking

### 4.6 Messaging

| ประเด็น | ดีไซน์เดิม | ปัจจุบัน | เลือก | เหตุผล |
|---|---|---|---|---|
| โครงห้องสนทนา | `conversations` + `conversation_members` (รองรับกลุ่ม) | คู่สนทนาบนแถว + UNIQUE(a,b) | **ปัจจุบัน** | ความต้องการคือลูกค้าคุยกับร้าน = คู่เสมอ การเก็บคู่ไว้บนแถวทำให้ฐานข้อมูล **บังคับเองได้** ว่าห้องซ้ำไม่ได้ ส่วนตาราง members บังคับไม่ได้ ต้องไปตรวจในโค้ด ราคาที่จ่ายคือทำแชทกลุ่มไม่ได้ ซึ่งไม่อยู่ในขอบเขต |
| สถานะอ่าน | ตาราง `message_reads` | `read_at` บนข้อความ | **ปัจจุบัน** | ห้อง 1:1 มีผู้รับคนเดียว ตารางแยกจะมีได้แค่ 1 แถวต่อข้อความเสมอ = ตารางเปล่าประโยชน์ |
| แนบไฟล์ | `message_attachments` | **ไม่มี** | **เดิม (ปรับ)** | ส่งรูปแบบเล็บให้ร้านดูคือฟีเจอร์หลักของระบบนี้ แต่ปรับให้ชี้ไป `assets` แทนการเก็บ `file_url`/`file_size`/`width`/`height` ซ้ำอีกที่ |
| ชนิดข้อความ | `message_type varchar` | มีแต่ข้อความล้วน | **เดิม (เป็น enum)** | ต้องแยกรูป/ข้อความระบบออกจากข้อความธรรมดา |
| แก้ไข/ลบ | `is_deleted` + `edited_at` | ✗ | **เดิม** | ส่งผิดแล้วลบไม่ได้ |
| บล็อกผู้ใช้ | คอมเมนต์ทิ้งไว้ ไม่ได้ใช้ | `user_blocks` | **ปัจจุบัน** | |

### 4.7 AI Assistant

| ประเด็น | ดีไซน์เดิม | ปัจจุบัน | เลือก | เหตุผล |
|---|---|---|---|---|
| บทสนทนา | `chat_sessions_ai` มี `user_id` FK | **ไม่มีตารางนี้** — `ai_chat_messages.session_id` ไม่ได้ชี้ไปไหนเลย | **เดิม** | นี่คือข้อผิดพลาดเชิงบูรณภาพจริงในสคีมาปัจจุบัน: ไม่รู้ว่าบทสนทนาเป็นของใคร ลบผู้ใช้แล้วข้อความค้างเป็นขยะ และตั้ง FK บังคับไม่ได้ |

## 7. การตรวจรูปแบบบรรทัดฐาน (Normalization)

### 7.1 First Normal Form

ทุกคอลัมน์เก็บค่าเดี่ยว มีข้อยกเว้นที่จงใจ 2 ประเภท

**ก. คอลัมน์ `jsonb` ที่เก็บ "เอกสาร"**
`design_versions.document`, `projects.draft_document`, `nail_templates.recipe`,
`color_palettes.colors`, `design_archetypes.default_params`, `assets.metadata`,
`notifications.data_json`

เหตุผล: ระบบอ่านค่าเหล่านี้ **ทั้งก้อนเสมอ** ไม่เคยถามใน SQL ว่า "ชั้นที่ 3 ของงานนี้สีอะไร"
ถ้าแตกเป็นตาราง `nail_layers` / `layer_effects` / `layer_gems` จะต้อง join 3–4 ตาราง
ทุกครั้งที่เปิดงานหนึ่งชิ้น เพียงเพื่อประกอบกลับเป็นก้อนเดิม
อีกทั้งโครงสร้างเปลี่ยนตามเวอร์ชันของโปรแกรม จึงมีคอลัมน์ `schema_version` กำกับไว้

**ข. `design_archetypes.supported_zones` เป็น array**
เป็นค่าคงที่ของระบบที่ทีมพัฒนา seed เอง ไม่ใช่ข้อมูลผู้ใช้ และไม่เคยถูก query แยกสมาชิก

ส่วน `shop_profiles.phone_numbers[]` ของสคีมาปัจจุบัน **ไม่เข้าข้อยกเว้น** เพราะเป็นข้อมูลผู้ใช้
ที่ต้องค้นและแสดงแยกรายการ จึงถูกแยกเป็นตาราง `shop_phones`

### 7.2 Second Normal Form

ตารางที่ใช้คีย์หลักผสม ต้องไม่มีคอลัมน์ที่ขึ้นกับคีย์เพียงบางส่วน — ตรวจแล้วผ่านทุกตาราง

| ตาราง | คีย์หลัก | คอลัมน์อื่น | ขึ้นกับคีย์ทั้งชุด |
|---|---|---|---|
| `template_category_map` | (template, category) | — | ✓ |
| `template_tag_map` | (template, tag) | `score`, `created_at` | ✓ |
| `template_likes` | (template, user) | `created_at` | ✓ |
| `template_ratings` | (template, user) | `score`, `created_at`, `updated_at` | ✓ |
| `user_blocks` | (blocker, blocked) | `created_at` | ✓ |

### 7.3 Third Normal Form

ไม่มี transitive dependency ยกเว้นค่าที่ **จงใจเก็บซ้ำเพื่อประสิทธิภาพ**

| คอลัมน์ | คำนวณจาก | ทำไมยอมเก็บซ้ำ |
|---|---|---|
| `nail_templates.like_count` และตัวนับอีก 5 ตัว | นับจากตารางลูก | ฟีด 20 โพสต์จะต้อง COUNT 6 ตาราง × 20 ครั้ง |
| `nail_templates.rating_avg` / `rating_count` | `template_ratings` | เรียงฟีดตามคะแนนโดยไม่ต้อง GROUP BY ทุกครั้ง |
| `shop_profiles.rating_avg` / `rating_count` | `shop_reviews` | เหตุผลเดียวกัน |
| `projects.version_count` | `design_versions` | แสดงในรายการงานทุกแถว |
| `conversations.last_message_at` | `conversation_messages` | เรียงรายการห้องแชทโดยไม่ต้อง join |
| `template_tags.usage_count` | `template_tag_map` | แสดงแท็กยอดนิยม |
| `template_share_links.view_count` / `copy_count` | `template_share_events` | |

**เงื่อนไขที่ต้องทำคู่กัน:** ทุกคอลัมน์ข้างต้นต้องมี trigger บนตารางลูก
(`AFTER INSERT/UPDATE/DELETE`) เป็นผู้ปรับค่า ไม่ใช่ให้โค้ดฝั่งแอปปรับเอง
มิฉะนั้นค่าจะเพี้ยนทันทีที่มีเส้นทางเขียนข้อมูลมากกว่าหนึ่งทาง

## 8. ข้อจำกัดที่ควรบังคับเพิ่มในระดับฐานข้อมูล

รายการนี้เขียนใน DBML ไม่ได้ ต้องเพิ่มเป็น `CHECK` / `EXCLUDE` / trigger ตอน migration

| ตาราง | ข้อจำกัด |
|---|---|
| `template_ratings` | `CHECK (score BETWEEN 1 AND 5)` |
| `shop_reviews` | `CHECK (rating BETWEEN 1 AND 5)` |
| `nail_templates` | `CHECK (difficulty BETWEEN 1 AND 5)` |
| `conversations` | `CHECK (participant_a_id < participant_b_id)` — ทำให้ UNIQUE(a,b) กันห้องซ้ำได้จริง |
| `user_blocks` | `CHECK (blocker_id <> blocked_id)` |
| `shop_opening_hours` | `CHECK (day_of_week BETWEEN 0 AND 6 AND open_time < close_time)` |
| `shop_time_off` | `CHECK (start_at < end_at)` |
| `appointments` | `EXCLUDE USING gist` — กันเวลานัดของร้านเดียวกันทับซ้อน เมื่อ `status = 'confirmed'` |
| `template_share_links` | `CHECK (expires_at IS NULL OR expires_at > created_at)` |
| `projects` | index แบบ partial `WHERE deleted_at IS NULL` |

## 9. สรุป

การเปรียบเทียบไม่ได้จบที่ "ชุดไหนดีกว่า" เพราะทั้งสองชุดเก่งคนละด้าน

- **สคีมาปัจจุบันวางแกนกลางถูก** โดยเฉพาะการแยกงานส่วนตัวออกจากการเผยแพร่
  การใช้ `timestamptz` / enum / token hash และการผูกรีวิวร้านกับการจองจริง
  สิ่งเหล่านี้แก้ทีหลังยากมาก และถ้าดีไซน์เดิมถูกสร้างจริงจะเจอปัญหาทั้งหมดนี้
- **ดีไซน์เดิมคิดฟีเจอร์รอบนอกไว้ครบกว่า** หมวดหมู่ แท็ก การให้ดาว ลิงก์แชร์
  ลืมรหัสผ่าน แนบไฟล์ในแชท เวลาทำการร้าน วันหยุด และ embedding
  สิ่งเหล่านี้เพิ่มทีหลังได้ แต่ปัจจุบัน "ยังไม่ได้เพิ่ม"

ฉบับสมบูรณ์จึงเก็บแกนกลางของปัจจุบันไว้ทั้งหมด แล้วเติมฟีเจอร์จากดีไซน์เดิม
พร้อมแก้จุดที่ *ทั้งสองชุดพลาดเหมือนกัน* อีก 3 จุด — บทบาทข้อความ AI ที่เป็นข้อความอิสระ
วงจรการตรวจรายงานที่ไม่ปิด และการที่ระบบรับรายงานได้แต่ลงโทษไม่ได้

**ผลลัพธ์: 39 ตาราง / 16 enum** — เพิ่มจากปัจจุบัน 14 ตาราง โดยทุกตารางตอบคำถามได้ว่า
ถ้าไม่มีแล้วระบบทำอะไรไม่ได้
