## 2 · การตัดสินใจที่ตกลงกันแล้ว

### D-A1 · กาง UV ใหม่ โดยยอมให้งานเก่าเพี้ยน

เส้นทุกเส้นถูกเก็บเป็น **พิกัด UV** (`toPaintPoint(u, v)` → `points: {x, y, p}`)
การกาง UV ใหม่ทำให้ผิวเล็บจุดเดิมย้ายไปอยู่พิกัดอื่น งานที่บันทึกไว้แล้วทั้งใน
`design_versions` (แก้ไม่ได้ตามหลัก immutable) และใน draft จะแสดงผลผิดตำแหน่ง

**เลือกยอมให้เพี้ยน** เพราะงานที่มีอยู่เป็นข้อมูลทดสอบล้วน ๆ ยังไม่มีผู้ใช้จริง
ทางเลือกที่พิจารณาแล้วไม่เอา:

| ทางเลือก | เหตุผลที่ไม่เลือก |
|---|---|
| เขียน migration ย้ายพิกัดเส้น (UV เก่า → จุดบนผิว → UV ใหม่) | ทำได้จริง แต่ต้องแตะ `design_versions` ที่ตั้งใจให้แก้ไม่ได้ — จ่ายราคาเชิงสถาปัตยกรรมเพื่อรักษาข้อมูลทดสอบ |
| ชดเชยที่หัวแปรงแทน (วาดวงรีให้ออกมากลม) | ปัญหาไม่หาย แค่ถูกกลบ และของตกแต่งใน C จะเจอปัญหาเดียวกันอีกรอบ |
| เลื่อนเรื่อง UV ออกไป | ต้องกลับมาสร้างโมเดลอีกรอบทั้งกระบวนการ |

### D-A2 · ความยาวเล็บเป็น morph target อีกชุด ไม่ใช่การสเกลตอนรันไทม์

ฐานคือ `round` + `medium` (ตรงกับ `createEmptyNail`) เพิ่ม shape key อีก 3 อัน
รวมเป็น **7 targets ต่อเล็บ** ทรงกับความยาวบวกกันได้เพราะ morph delta เป็นเวกเตอร์

**เหตุผล**: ทรงและความยาวเกิดจากที่เดียวกัน ตรวจด้วยด่านเดียวกัน และรันไทม์ไม่ต้อง
รู้เรื่องเรขาคณิตเลยนอกจากตั้งตัวเลข ที่สำคัญกว่านั้นคือ assertion **"โคนเล็บขยับ = 0"**
ครอบคลุมความยาวได้ฟรีโดยไม่ต้องเขียนด่านใหม่

ทางเลือกที่พิจารณาแล้วไม่เอา:

| ทางเลือก | เหตุผลที่ไม่เลือก |
|---|---|
| สเกลตามแกนยาวตอนรันไทม์ (ได้ความยาวต่อเนื่อง) | ต้องดัด geometry ที่ผ่าน skinning มาแล้ว — จุดที่ S2 พลาดมาแล้ว และย้ายด่านตรวจโคนเล็บไปฝั่งรันไทม์ซึ่งตรวจอัตโนมัติยากกว่ามาก |
| อบทุกคู่ 5 ทรง × 4 ความยาว = 20 targets | ไฟล์โต ~4% แต่ที่แย่กว่าคืองานเชิงศิลป์คูณ 20 ทั้งที่ S2 บอกว่าแค่ปรับ square/squoval สองตัวก็ยังไม่ลงตัว |

จำนวน target ไม่ใช่ข้อจำกัด — three.js รุ่นปัจจุบันส่ง morph ผ่าน texture ไม่ติดเพดาน 8 แบบเดิม
และ S2 วัดแล้วว่า 4 targets เพิ่มไฟล์ 0.83% ประมาณได้ว่า 7 targets จะอยู่ราว 1.5%

## 3 · โครงไปป์ไลน์

(`nail_unwrap.py` เขียนคอมเมนต์ว่า "ไม่ import bpy จึงเทสได้ด้วย python ปกติ" —
หลักการถูก แค่ตัวโค้ดถูกลบไป) เหตุผลจริงคือ **เทสที่ต้องเปิด Blender ทุกครั้งจะไม่มีใครรัน**

| ไฟล์ | หน้าที่ | ต้อง Blender |
|---|---|---|
| `model/hand_source.glb` | โมเดลต้นทาง 11.2 MB ย้ายเข้ามา | — |
| `tools/nail_geometry.py` | PCA · ดัดทรง · ดัดความยาว · ฉาย UV · วัดความบิด | **ไม่** |
| `tools/test_nail_geometry.py` | เทสของข้างบน รันด้วย python ธรรมดา | **ไม่** |
| `tools/build_shapes.py` | สร้าง shape key 7 อันต่อเล็บ | ใช่ |

| `tools/verify_model.py` | ด่านตรวจไฟล์ที่ออกมา | ใช่ |

`hand_source.glb` เข้า git เพราะ repo นี้ commit `hand.glb` 11.7 MB อยู่แล้ว
การเก็บผลลัพธ์แต่ไม่เก็บต้นทางแปลว่าสร้างซ้ำไม่ได้

### ลำดับใน `build_model.py`

```
import → ล้างของแปลกปลอม → ซ่อม normal → แบ่งย่อยเล็บ → กาง UV ใหม่
  → สร้าง shape key 7 อัน → ตัด action → ตรวจ rig → เปลี่ยนชื่อ → export
```

**สามขั้นกลางสลับกันไม่ได้**:

- shape key ผูกกับจำนวน vertex — แบ่งย่อยทีหลัง morph ทั้งชุดใช้ไม่ได้
- UV ต้องกางหลังแบ่งย่อย เพราะจุดที่เพิ่มมาต้องมีพิกัดด้วย
- ซ่อม normal ก่อนทุกอย่าง เพราะ `fix_nail_normals` กลับลำดับจุดของหน้า
  ซึ่งจะทำให้ delta ของ shape key ที่สร้างไว้ก่อนหน้าชี้ผิดตัว

### การแบ่งย่อย

เล็บมี vertex ไม่เท่ากันเลย: `Nail_index` 81 · `Nail_middle` 197 · `Nail_little` 201 ·
`Nail_thumb` 203 · `Nail_ring` 289 (วัดใน S2) S2 §6 ระบุว่า 81 อาจไม่พอสำหรับมุมคม

แบ่งย่อยจนแต่ละเล็บมี **อย่างน้อย 300 vertices** สูงสุด 2 ระดับ และ log ค่าก่อน/หลังทุกชิ้น
ต้นทุนคือสามเหลี่ยมหลักร้อยเทียบกับมือ 118,756 tris

**ความเสี่ยงที่ต้องกัน**: การแบ่งย่อย mesh ที่ผูก armature ทำให้ Blender สอดแทรกน้ำหนัก
vertex group ให้เอง ซึ่งอาจไม่รวมเป็น 1 → เพิ่มด่านตรวจ (ข้อ 4.4)

## 4 · ด่านตรวจใน `verify_model.py`

ด่านเดิมคงไว้ทั้งหมด เพิ่มใหม่ 4 ข้อ

### 4.1 · morph ครบ 7 ต่อเล็บ

`extras.targetNames` ต้องเป็น `almond · square · squoval · stiletto · short · long · extra`
เรียงตรงตามลำดับ และมีครบทั้ง 5 เล็บ

### 4.2 · โคนเล็บขยับ = 0 ทุก target

ยก assertion จาก S2 มาเป็นด่านจริง — vertex ที่อยู่ในช่วง `g ≤ 0.1` (10% แรกจากโคนเล็บ
ตามแกน PCA) ต้องมีระยะขยับ `< 1e-6` เมตรในทุก target

ด่านนี้ผ่านได้เพราะ §6 บังคับให้ทุกสูตรคูณด้วย `r(g)` ซึ่งเป็นศูนย์ตลอดช่วงนั้น
ถ้าวันหนึ่งมีคนเพิ่มทรงใหม่แล้วลืมคูณ ด่านนี้จะจับได้ทันที — นั่นคือหน้าที่ของมัน

S2 วัดได้ `0.000` ทุกเล็บ ถ้าค่านี้ไม่เป็นศูนย์ เล็บจะหลุดลอยจากผิวนิ้วทันทีที่ผู้ใช้
เปลี่ยนทรง — เป็นข้อบกพร่องที่เห็นได้ด้วยตาทันที และเป็นสิ่งที่ D-10 สัญญาไว้ว่าจะไม่เกิด

### 4.3 · ความบิดของ UV — ด่านที่สำคัญที่สุดของรอบนี้

สำหรับทุกสามเหลี่ยม หาอัตราส่วนการยืดจากเมทริกซ์ที่พาสามเหลี่ยมบน UV ไปเป็นสามเหลี่ยม
บนผิวจริง (ค่าเอกฐาน σmax / σmin) แล้วบังคับ:

```
max ทุกสามเหลี่ยม (σmax / σmin) ≤ 1.15
```

**ด่านนี้เปลี่ยน "รอยแปรงกลมไหม" จากการเถียงด้วยตาเป็นตัวเลขที่พิสูจน์ได้**
ค่าปัจจุบันคือ **1.4** ตามที่วัดไว้ใน D-25 (จึงเห็นรอยแปรงเป็นวงรี 1.4:1)

เกณฑ์ 1.15 ตั้งไว้ล่วงหน้า **ค่าที่วัดได้จริงต้องรายงานกลับมาตามจริง** ห้ามขยับเกณฑ์
ให้พอดีกับผลลัพธ์ทีหลัง ถ้าทำไม่ถึงต้องบันทึกว่าทำไมและเหลือเท่าไร

**ค่าจริงที่วัดได้ (task 4, รันด่าน `check_uv_distortion` จริงกับ `hand.glb` ที่ task 3
สร้าง — 2026-08-14):**

| เล็บ   | ความบิด UV วัดได้ | ≤ 1.15 ? |
|--------|-------------------:|----------|
| thumb  | 25.543              | ไม่ผ่าน ห่างมาก |
| index  | 1.792               | ไม่ผ่าน |
| middle | 3.262               | ไม่ผ่าน |
| ring   | 1.544               | ไม่ผ่าน |
| little | 5.428               | ไม่ผ่าน |

ทุกเล็บไม่ผ่านเกณฑ์ thumb เกินเกณฑ์ 1.3 ที่กำหนดไว้ด้านล่างอย่างมาก (25.543 ≫ 1.3)
ตามกฎที่วางไว้ ต้องพิจารณาทางเลือกที่สอง — LSCM/ABF ของ Blender (ดู §5) — ก่อนไปต่อ
task ถัดไป การตัดสินใจนี้ปล่อยให้ผู้ควบคุม/ผู้ใช้เป็นคนตกลง ยังไม่ได้ลงมือทำใน task
นี้ (นอกขอบเขตของ task 4 ซึ่งมีหน้าที่แค่เพิ่มด่านตรวจและรายงานค่าจริง)

### 4.4 · น้ำหนัก skin ยังรวมเป็น 1

ทุก vertex ของทุกเล็บ `|Σw − 1| < 1e-4` — กันความเสียหายจากการแบ่งย่อย

### รายงานที่ต้องพิมพ์ออกมาเสมอ (ไม่ใช่ด่าน แต่ต้องมี)

## 5 · การกาง UV ใหม่

ใช้วิธีเดียวกับ `nailFlatten.ts` ที่เขียนไว้แล้วใน Slice 2:

```
1. หาแกนด้วย PCA — e0 แกนยาว (โคน→ปลาย) · e1 แกนกว้าง · e2 แกนหนา
2. ฉายจุดยอดลงระนาบ (e0, e1)  — ทิ้งความหนาไป
3. ย่อลงกรอบ 0–1 แบบ **คงสัดส่วน** (สเกลเดียวกันทั้งสองแกน) เว้นขอบ **6%**
```

ค่าขอบ 6% คัดลอกมาจาก `PADDING = 0.06` ใน `nailFlatten.ts` ตรง ๆ (ไม่ใช่ 4% ตามที่เขียน
ในฉบับร่างแรกของหัวข้อนี้ — เผลอจำผิดตอนร่างสเปก ต้องใช้ค่าเดียวกับโค้ดจริงเป๊ะ ไม่งั้น
"ตรงกันโดยโครงสร้าง" ที่อ้างไว้ด้านล่างจะไม่จริง)

**ผลข้างเคียงที่ตั้งใจ**: หลังทำเสร็จ `nailFlatten.ts` จะกลายเป็นการแปลงที่เกือบเป็น
เอกลักษณ์ เพราะทั้งสองฝั่งใช้นิยามเดียวกัน แผงวาด 2 มิติกับผืนเท็กซ์เจอร์จะตรงกัน
**โดยโครงสร้าง ไม่ใช่โดยบังเอิญ** และถ้าวันหนึ่งมันไม่ตรง แปลว่ามีฝั่งใดฝั่งหนึ่งผิด
ซึ่งเป็นสัญญาณที่มีค่ามากกว่าความบังเอิญที่ใช้ได้

**ข้อจำกัดที่รู้ตัว**: การฉายลงระนาบมีความบิดที่ขอบเล็บซึ่งโค้งลง เล็บเป็นผิวตื้น
ค่าจึงน่าจะน้อย แต่ **ไม่เดา — ด่าน 4.3 เป็นตัววัด** ถ้าผ่านไม่ได้ ทางถัดไปคือ
LSCM/ABF ของ Blender ซึ่งลดความบิดได้ดีกว่าแต่ไม่รับประกันว่าผลจะตรงกับ `nailFlatten.ts`
(จะเสียสมบัติ "ตรงกันโดยโครงสร้าง" ไป จึงเป็นทางเลือกที่สอง ไม่ใช่ทางแรก)

## 6 · แบบจำลองการดัด

ให้ `g ∈ [0,1]` คือตำแหน่งตามแกน e0 โดย `g = 0` ที่โคนเล็บ `g = 1` ที่ปลาย
และ `w̄ ∈ [0,1]` คือระยะจากแกนกลางตามแกน e1 ที่ปรับเป็นสัดส่วนแล้ว
`L` คือความยาวจริงของเล็บชิ้นนั้น

### กฎข้อเดียวที่ทุกสูตรต้องเคารพ — แก้ไขระหว่างทำแผนลงมือ

**เวอร์ชันแรกของหัวข้อนี้ผิด** ตอนเขียนสเปกยังไม่ได้เปิดโค้ด spike จริง
(`spikes/s2-nail-shapes/make_shapes.py`) เขียนจากการจำเนื้อหาในเอกสาร S2 แล้วคาดเดา
ค่า `g₀ = 0.1` เอาเอง พอเปิดโค้ดจริงตอนทำแผนลงมือ พบว่า S2 ที่วัดผลไว้แล้วและยืนยันว่า
"โคนเล็บขยับ = 0.000" ใช้ค่าคนละตัว — **`TAPER_START = 0.45`** ไม่ใช่ 0.1 ยังใช้ตัวคูณ
สูตรเดิมของ S2 ต่อไม่ได้ถ้าไม่แก้ค่านี้ให้ตรงกับที่วัดผลไว้จริง

```python
# spikes/s2-nail-shapes/make_shapes.py — ต้นทางที่ถูกต้อง
def taper_weight(t01):
    raw = np.clip((t01 - 0.45) / (1.0 - 0.45), 0.0, 1.0)
    return raw * raw
```

ให้ `r(g)` เป็นตัวประกอบร่วมที่คูณอยู่กับการขยับทุกชนิด โดยยกสูตรนี้มาตรง ๆ:

```
r(g) = 0                              เมื่อ g ≤ 0.45
r(g) = ((g − 0.45) / 0.55)²           เมื่อ g > 0.45
```

**การขยับทุกสูตรต้องคูณด้วย `r(g)`** ผลคือแถบโคนเล็บ 45% แรกนิ่งสนิท *โดยโครงสร้าง*
ไม่ใช่โดยบังเอิญที่ต้องมาวัดทีหลัง — ด่าน 4.2 จึงเป็นการยืนยันว่าโค้ดทำตามกฎนี้จริง
ไม่ใช่การหวังว่าตัวเลขจะออกมาดี

ยกกำลังสองแทนเชิงเส้นเพราะอนุพันธ์เป็นศูนย์ที่ `g = 0.45` ด้วย (เอกสาร S2 §2 อธิบายไว้แล้ว)
ถ้าใช้เชิงเส้นตรง ๆ จะเกิดสันหักตรงขอบแถบ ซึ่งมองเห็นเป็นรอยพับบนผิวเล็บตอนแสงตกกระทบ

**ด่าน 4.2 ที่ตั้งไว้ว่า "vertex ในช่วง `g ≤ 0.1` ต้องขยับ `< 1e-6`" ยังใช้ได้ไม่ต้องแก้**
เพราะ 0.1 < 0.45 ด่านนี้เป็นขอบล่างที่ปลอดภัยกว่าเขตที่นิ่งจริง (45%) ไม่ใช่ขอบเขตที่พอดี
เขียนด่านแบบระวังไว้ก่อนแบบนี้ตั้งแต่ต้น — ไม่ใช่เรื่องบังเอิญที่มันยังผ่าน

### ทรง — ยกสูตรจาก `make_shapes.py` ตรงตัว ไม่ต้องคิดใหม่

ให้ `w̄ = |w| / max(|w|)` (ระยะจากแกนกลางตามแกน e1 แบบ normalize แล้ว) และ `L = span`
คือความยาวจริงตามแกน e0 ผลลัพธ์เป็นส่วนต่างของ `(t, w, d)` แล้วแปลงกลับด้วย
`Δ = Δt·e0 + Δw·e1 + Δd·e2` ก่อนบวกเข้ากับพิกัดเดิม (คัดลอกจาก `deform()` บรรทัด 94–115
ของ `make_shapes.py` ทุกตัวเลข — **นี่คือค่าที่ S2 วัดผลจริงและยืนยันว่าใช้ได้แล้ว**):

| ทรง | `Δt` | `Δw` | `Δd` |
|---|---|---|---|
| `almond` | `(1 − w̄) · 0.10 · L · r(g)` | `−w · 0.55 · r(g)` | `0` |
| `stiletto` | `(1 − w̄) · 0.34 · L · r(g)` | `−w · 0.85 · r(g)` | `0` |
| `square` | `w̄ · 0.11 · L · r(g)` | `w · 0.18 · r(g)` | `0` |
| `squoval` | `w̄ · 0.055 · L · r(g)` | `w · 0.06 · r(g)` | `0` |

**S2 §6 ระบุว่า square/squoval จางเกินไปที่ระยะมองทั้งมือ** ค่าในตารางนี้คือค่าตั้งต้น
ที่ต้องปรับแรงขึ้นตามคำแนะนำของ S2 (`0.20–0.25·L` สำหรับ square) แต่**ต้องปรับบนฐาน
สูตรที่ถูกต้องนี้** ไม่ใช่บนสูตร `r(g)` แบบเก่าที่ผิดซึ่งเขียนไว้ในฉบับร่างแรกของหัวข้อนี้
almond/stiletto ใช้ได้ตามนี้ตรง ๆ ไม่ต้องปรับ (S2 ยืนยันด้วยภาพเรนเดอร์แล้ว)

S2 §6 ยังเสนอ "ตัดมุม" — ที่ `w̄ > 0.8` ให้ขยับน้อยลง เพื่อให้ได้มุมฉากจริง
ไม่ใช่ส่วนโค้งที่แบนลง จะทดลองหลังปรับความแรงพื้นฐานแล้ว

### ความยาว

ขยับตามแกน e0 ด้วยระยะ `(k − 1) · L · r(g)` — โคนนิ่งสนิท ปลายขยับเต็ม
ใช้ `r(g)` เดียวกับทรงทุกประการ (มาตรฐานเดียวกันทั้งไฟล์)

| ความยาว | `k` | หมายเหตุ |
|---|---|---|
| `short` | 0.75 | ดึงปลายเข้า |
| `medium` | 1.00 | ฐาน ไม่มี target |
| `long` | 1.30 | |
| `extra` | 1.60 | |

ค่าเหล่านี้เป็นจุดเริ่ม ต้องดูภาพเรนเดอร์แล้วปรับ เหมือนที่ `THUMB_ROLL` ในซอร์สเดิม
บันทึกค่าที่ลองไว้ในคอมเมนต์พร้อมเหตุผล — จะทำแบบเดียวกัน

## 7 · ฝั่งรันไทม์

### โมดูลใหม่

`apps/web/src/3d/models/nailMorphs.ts` — แปลง `(shape, length)` เป็นอาร์เรย์ influence
ตาม `morphTargetDictionary` ของ mesh ฟังก์ชันบริสุทธิ์ เทสได้โดยไม่ต้องมี WebGL

### เข้าระบบ history

`SetShapeCommand` · `SetLengthCommand` เดินตามแบบ `SetFinishCommand` ทุกประการ
(รับ `mergeKey` · ทำงานกับ `editableSelection` ผ่าน `CompositeCommand`) และ
`<select>` สองตัวในแถบเครื่องมือถัดจาก "ผิวเล็บ"

### จุดที่ต้องระวัง — ยังไม่มีใครเขียนไว้ที่ไหน

`nailViews.ts` และ `nailFlatten.ts` อ่าน `geometry.attributes.position` ตรง ๆ
ซึ่งเป็น **ทรงฐาน ไม่รวม morph** ผลคือเมื่อผู้ใช้เลือก `stiletto`:

- การจ่อกล้องจะเล็งผิดจุด (คำนวณจากเล็บทรง round)
- รูปบนแผงวาด 2 มิติจะไม่ตรงกับเล็บจริงบนจอ

ต้องบวก `Σ influence_i × delta_i` เข้ากับตำแหน่งฐานก่อนพับเมทริกซ์กระดูก
**เป็นบั๊กตระกูลเดียวกับ `geometry.boundingSphere` ที่ค้างอยู่ท่า rest** ซึ่ง
`nailViews.ts` ของซอร์สเดิมเขียนคอมเมนต์เตือนไว้ และ S2 ยังเผลอทำซ้ำระหว่างทำ spike
→ ต้องมีเทสที่พิสูจน์ว่าเปลี่ยนทรงแล้วรูปบนแผง 2 มิติเปลี่ยนตาม
