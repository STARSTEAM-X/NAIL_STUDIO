## 1 · นิยาม "ใช้งานได้จริง" (Definition of Production-Ready)

โครงงานนี้ต้อง **ใช้งานได้จริง** ไม่ใช่สาธิตได้ ดังนั้นต้องนิยามให้เป็นเช็คลิสต์ที่ตรวจได้
ไม่ใช่ความรู้สึก — เกณฑ์ 8 ข้อนี้ใช้กับ**ทุกฟีเจอร์ที่ประกาศว่าเสร็จ**

| # | เกณฑ์ | วิธีพิสูจน์ |
|---|---|---|
| P1 | **ข้อมูลผู้ใช้ไม่หาย** | ปิดเน็ต / ปิดแท็บกลางคัน / เซิร์ฟเวอร์ล่ม → งานยังกู้คืนได้ (มีเทสจำลองทั้ง 3 กรณี) |
| P2 | **error ไม่ทำให้หน้าขาว** | ทุก route มี error boundary; ทุก error มีข้อความที่บอกว่าเกิดอะไรและทำอย่างไรต่อ |
| P3 | **ไม่รั่ว secret / stack trace / path ระบบ** | เทสอัตโนมัติยิง error ทุกชนิดใน production build แล้วตรวจ response |
| P4 | **ทำงานบนเครื่องจริง ไม่ใช่แค่เครื่องเรา** | ทดสอบบนมือถือจริง 2 เครื่อง + เบราว์เซอร์ 3 ตัว + Linux container |
| P5 | **คนอื่น deploy ตาม README ได้** | ให้คนที่ไม่เคยเห็นโปรเจกต์ทำตามแล้วรันได้จริง (บันทึกว่าติดตรงไหน) |
| P6 | **มีตัวเลข performance ที่วัดจริง** | `docs/performance.md` มีสภาพแวดล้อมการวัดที่ทำซ้ำได้ |
| P7 | **ผู้ใช้ A แตะข้อมูลผู้ใช้ B ไม่ได้** | เทส authorization ทุก endpoint ที่มีเจ้าของ |
| P8 | **สังเกตการณ์ได้** | structured log + request id + health check + ตัวนับ error |

**ระดับคุณภาพที่ประกาศไว้ล่วงหน้า** — โครงงานที่ทำ 5 ผลิตภัณฑ์ในเวลาจำกัด
การประกาศระดับคุณภาพอย่างตรงไปตรงมาเป็นความซื่อสัตย์ทางวิชาการ **มากกว่า**
การแกล้งทำเป็นว่าทุกส่วนขัดเงาเท่ากัน:

| ระดับ | เกณฑ์ | ครอบคลุม |
|---|---|---|
| **Tier 1 — Production** | ครบ P1–P8 + coverage ≥ 85% + benchmark ครบ | auth · projects · **3D editor** · persistence · ความปลอดภัย |
| **Tier 2 — Complete** | ครบ P1–P8 + coverage ≥ 70% + benchmark หลัก | template/community · AI generate · ระบบร้าน/นัดหมาย/รีวิว |
| **Tier 3 — Functional** | ครบ P1–P4, P7 + เทส flow หลัก + **ระบุข้อจำกัดไว้ในเอกสารชัดเจน** | AI chat · VR preview |

**เหตุผลของการจัดระดับ**: แกนที่ทำให้โครงงานนี้ต่างจากโครงงานอื่นคือ **3D editor**
— pipeline วาดบน UV, BVH, dirty update, Command pattern — และเป็นที่อยู่ของข้อกำหนด
ด้านอัลกอริทึม/ความซับซ้อนทั้งหมด จึงต้องเป็น Tier 1 ส่วน VR และ chat เป็นฟีเจอร์เสริม
ที่แสดงความกว้าง ไม่ใช่ความลึก

## 2 · ทำไมเปลี่ยนเป็นแผนแนวตั้ง

**แผนเดิม (แนวนอน)**: backend ทั้งก้อน → frontend ทั้งก้อน → 3D ทีละชั้น → persistence

ปัญหา: **ครั้งแรกที่ระบบทำงานครบวงจรคือสัปดาห์ที่ 14** ถ้าอะไรพังตรงนั้นไม่เหลือเวลาแก้
และตลอด 13 สัปดาห์แรกไม่มีอะไรสาธิตให้อาจารย์ที่ปรึกษาดูได้

**แผนใหม่ (แนวตั้ง)**: สัปดาห์ที่ 4 ต้องมี

```
ล็อกอิน → สร้างงาน → เห็นมือ 3D → บันทึก → รีโหลด → งานยังอยู่
```

บางมาก แต่**ทะลุทุกชั้นจริง** (React → Zustand → TanStack Query → Express → Service →
Repository → PostgreSQL → กลับมา → R3F → Three.js) หลังจากนั้นทุกสัปดาห์มีของสาธิตได้เสมอ

| ข้อดี | ผล |
|---|---|
| ความเสี่ยงเชิงบูรณาการถูกเปิดโปงตั้งแต่สัปดาห์ที่ 4 | ปัญหาแบบ "CORS + cookie ข้าม origin" หรือ "R3F ไม่ทำงานกับ React 19" เจอตอนที่ยังแก้ได้ |
| มีของสาธิตตลอดเวลา | ประกันชีวิตของโครงงานที่มีเดดไลน์ตายตัว |
| ตัดขอบเขตได้ตอนท้ายโดยไม่พัง | ถ้าเวลาไม่พอ ตัด slice ท้าย ๆ ทิ้งได้ ระบบยังสมบูรณ์ในตัว |
| ทดสอบ E2E ได้ตั้งแต่ต้น | flow หลักมีเทสคุ้มกันตั้งแต่สัปดาห์ที่ 4 ไม่ใช่สัปดาห์ที่ 20 |

## 4 · Slice 1 — Walking Skeleton (สัปดาห์ 3–4)

**เป้าหมาย**: เส้นทางบางที่สุดที่ทะลุทุกชั้นของระบบ

```
สมัคร → ล็อกอิน → สร้างโปรเจกต์ → เปิด editor → เห็นมือ 3D →
กดบันทึก (document ว่าง) → รีเฟรช → เปิดงานเดิม → ยังเห็นมือ
```

| ชั้น | ทำแค่ไหน |
|---|---|
| monorepo + CI | ครบ (workspaces, tsconfig strict, ESLint, CI บน **ubuntu-latest**) · **สแตกที่ยืนยันแล้ว**: React 19.2.8 · R3F 9.7.0 · drei 10.7.8 · three 0.185.1 · TS 7.0.2 · Vite 8.2.1 · plugin-react 6.0.5 · ทุกแพ็กเกจ frontend ต้องมี `src/vite-env.d.ts` |
| **ปิดความเสี่ยงที่ค้างจาก S1b** | ทดสอบ **TS 7 กับ Prisma Client / Express / Zod / Vitest** — ถ้าพัง ตรึง TS คนละเวอร์ชันต่อ workspace ได้ ไม่ต้องถอยทั้งโปรเจกต์ |
| `packages/contracts` | `DesignDocument` schema + pipeline Zod → JSON Schema → Pydantic (D-13) |
| Postgres + Prisma | แค่ `users`, `sessions`, `projects`, `design_versions` — ยังไม่ต้องครบ 28 ตาราง |
| API | `register`, `login`, `me`, `logout`, `projects` CRUD, `versions` create/get |
| Auth | Argon2id + session cookie httpOnly + CSRF (**ทำให้ถูกตั้งแต่แรก ไม่ทำทีหลัง**) |
| Web | router + AuthProvider + TanStack Query + หน้า login/projects/editor |
| 3D | `Stage` + `HandModel` + `OrbitControls` — ยังไม่มีการวาด |
| E2E | flow ข้างบน 1 เทส |

**Definition of Done** — สถานะ ณ 2026-08-12

- [x] flow ข้างบนทำงานจริงบนเบราว์เซอร์ ไม่ใช่แค่ผ่านเทส — **ยืนยันด้วยตาแล้ว**
      (สมัคร → สร้างงาน → เปิด editor → เห็นมือ 3D + เล็บ 5 ชิ้น → บันทึก → รีโหลด → เวอร์ชัน 2)
- [x] ผู้ใช้ A เปิดโปรเจกต์ของผู้ใช้ B ไม่ได้ (ตอบ 404 ไม่ใช่ 403) — มีเทสคุ้มกัน
- [x] typecheck ผ่านทั้ง 3 workspace (TS 7 strict + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes`)
- [x] เทสผ่าน 30 รายการ — contracts 8 · api 15 (integration กับ PostgreSQL จริง) · web 7
- [x] **migration จริงใช้งานได้** — baseline `0_init` + เครื่องมือ `npm run db:verify`
      ที่พิสูจน์ว่า migration รันจากฐานข้อมูลเปล่าได้จริง ตรวจตาราง คอลัมน์
      ข้อจำกัดความไม่ซ้ำ และดัชนี **โดยไม่แตะฐานข้อมูลจริง** (สร้าง scratch DB แล้วลบทิ้ง)
- [ ] CI เขียวบน Linux (จับบั๊ก case-sensitivity CD-1) — **ยังไม่ได้ตั้ง GitHub Actions**
- [ ] `docker compose up` แล้วคนอื่นรันตามได้ — เครื่องพัฒนาไม่มี Docker ใช้ PostgreSQL ตรง (ดู `SETUP.md`)
- [ ] เปิด-ปิด editor 10 รอบ หน่วยความจำไม่โตสะสม
- [ ] **บันทึก baseline benchmark** — fps/frame time ในหน้าต่างปกติ (M1 ใน performance.md)

**บทเรียนที่ได้จาก Slice 1 (ต้องนำไปใช้ทุก slice)**

| บทเรียน | ที่มา |
|---|---|
| **อย่าใช้ PowerShell จัดการไฟล์ของโปรเจกต์** | เจอกับดักการเข้ารหัส 3 แบบ: `Out-File -Encoding utf8` ใส่ BOM · `Get-Content -Raw` อ่านเป็น ANSI · ไฟล์ `.ps1` ที่ไม่มี BOM ถูกอ่านเป็น ANSI · และ `ConvertTo-Json` ทำ JSON เละ → **ใช้เครื่องมือแก้ไฟล์โดยตรงเสมอ** |
| **ห้ามใส่ connection string ใน argv** | สคริปต์ตรวจ migration ของผมทำให้รหัสผ่านฐานข้อมูลโผล่ในข้อความ error → ส่งผ่าน env เท่านั้น |
| **Prisma ปฏิเสธคำสั่งทำลายข้อมูลเมื่อถูกเรียกโดย AI agent** | `migrate reset` ถูกบล็อก — เป็นการป้องกันที่ถูกต้อง ให้หาทางตรวจแบบไม่ทำลายแทน |
| **`pg` ไม่แปลง `name[]` เป็น JS array** | ต้อง cast `::text[]` ไม่งั้นได้สตริงดิบ `{email}` แล้วโค้ดวนตัวอักษรทีละตัวโดยไม่มี error ให้จับ |
| **Prisma สร้าง `@unique` เป็น unique index ไม่ใช่ table constraint** | การตรวจจาก `information_schema.table_constraints` จะไม่เจอ ต้องอ่าน `pg_index` |

> ตั้งแต่จุดนี้เป็นต้นไป **ห้ามให้ CI แดงข้ามคืน** และห้าม merge อะไรที่ทำให้ flow นี้พัง

   - รวม **การประเมินโดยมนุษย์** ของกฎสี A-22 (คน 5 คน × ดีไซน์ 50 ชิ้น)
4. **ตรวจทานย้อนกลับ**: ทุกคำกล่าวอ้างความซับซ้อนต้องสอดคล้องกับผลที่วัดได้ —
   ไม่ตรง → **แก้เอกสาร ไม่ใช่แก้ตัวเลข**
5. Dockerfile หลาย stage (web/api/ai) non-root + `docker-compose.prod.yml` + nginx
6. `S3Provider` จริง (พิสูจน์ D-09 ว่าสลับได้โดยไม่แก้ service)
7. Backup อัตโนมัติ + **ทดสอบ restore จริง**
8. `docs/deployment.md` + README ที่ **ให้คนอื่นลองทำตามจริง** (P5)
9. `docs/assets-license.md` (ปิด R-8)

**DoD**: ไม่มีคำว่า `ยังไม่ได้วัด` เหลือใน `algorithms.md` ·
`docker compose -f docker-compose.prod.yml up` ได้ระบบใช้งานได้จากศูนย์ ·
restore จาก backup สำเร็จข้อมูลครบ ·
**มีอย่างน้อย 1 กรณีที่ผลการวัดขัดกับที่คาดไว้ พร้อมการวิเคราะห์ว่าทำไม**
(ถ้าไม่มีเลย แปลว่าวัดไม่ละเอียดพอ)
