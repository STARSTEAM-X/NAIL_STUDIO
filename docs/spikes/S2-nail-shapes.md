## 2 · วิธีที่ใช้ — PCA + การดัดตามแกน

```
1. หาแกนหลักด้วย PCA (eigen decomposition ของเมทริกซ์ความแปรปรวนร่วม 3×3)
   e0 = แกนยาว (โคนเล็บ → ปลายเล็บ)   e1 = แกนกว้าง   e2 = แกนหนา
2. ตัดสินว่าปลายไหนคือปลายเล็บ โดยเทียบความกว้างของ 25% แรกกับ 25% สุดท้าย
   — ฝั่งที่แคบกว่าคือปลายเล็บ
3. แปลงทุกจุดเป็น (t, w, d) แล้ว normalize t ให้อยู่ใน [0,1]
4. น้ำหนักการดัด g(t) = clamp((t − 0.45) / 0.55, 0, 1)²
   → เป็น 0 ที่โคนเล็บ 1 ที่ปลาย และเรียบต่อเนื่อง (ยกกำลังสองกันรอยหัก)
5. สร้าง shape key หนึ่งอันต่อทรง → export เป็น morph target
```

**ทำไมต้องยกกำลังสอง**: ถ้าใช้ linear ramp จะเห็นรอยหักตรง t = 0.45 เป็นสันชัดเจน
บนผิวเล็บที่ควรเรียบ

**ทำไม `np.linalg.eigh` ไม่ใช่ `eig`**: เมทริกซ์ความแปรปรวนร่วมเป็น symmetric เสมอ
`eigh` เร็วกว่าและคืนค่าจริงเสมอ (`eig` อาจคืนจำนวนเชิงซ้อนจาก error การปัดเศษ)

**ความซับซ้อน**: สร้าง covariance `O(V)` · eigen ของเมทริกซ์ 3×3 `O(1)` ·
ดัดหนึ่งทรง `O(V)` → ทั้งหมด `O(S · N · V)` = 4 ทรง × 5 เล็บ × ≤289 verts
≈ 5,800 การดำเนินการ **ทำครั้งเดียวตอน build ไม่ใช่ runtime**

### สูตรของแต่ละทรง

| ทรง | สูตร | เหตุผล |
|---|---|---|
| `round` | — (ทรงพื้นฐานของโมเดลต้นทาง) | ไม่ต้องมี shape key |
| `almond` | `t += (1−w̄)·0.10·L·g` · `w ×= 1 − 0.55g` | สอบปลายเข้าหาแกนกลาง แล้วยืดกลางออกให้ปลายมนแหลม |
| `stiletto` | `t += (1−w̄)·0.34·L·g` · `w ×= 1 − 0.85g` | เหมือน almond แต่สอบแรงกว่าและยาวกว่ามาก |
| `square` | `t += w̄·0.11·L·g` · `w ×= 1 + 0.18g` | **ดันขอบข้างไปข้างหน้าให้ทันจุดกึ่งกลาง** ทำให้ขอบหน้าที่เดิมโค้งกลายเป็นเส้นตรง |
| `squoval` | เหมือน square ครึ่งแรง + สอบเล็กน้อย | สี่เหลี่ยมมุมมน |

`w̄` = `|w| / max|w|` (ระยะห่างจากแกนกลางแบบ normalize)

**หัวใจของทรง square** อยู่ที่การคูณด้วย `w̄` — ขอบเล็บ (`w̄ ≈ 1`) ขยับไปข้างหน้ามาก
ส่วนจุดกึ่งกลาง (`w̄ ≈ 0`) แทบไม่ขยับ ผลคือส่วนโค้งด้านหน้าถูกดัดให้แบนลงเป็นเส้นตรง

## 6 · สิ่งที่ต้องปรับต่อ (งานเชิงศิลป์ ไม่ใช่เชิงเทคนิค)

**ค่าความแรงของ square/squoval ตั้งไว้ระมัดระวังเกินไป** — `0.11·L` และ `0.055·L`
ให้ผลที่ปลอดภัยแต่ไม่มีบุคลิก ผู้ใช้ที่เลือก "square" คาดหวังปลายตัดตรงที่เห็นชัด

แนวทางแก้ที่ต้องทดลองใน Slice 4:

1. เพิ่มความแรงเป็น `0.20–0.25·L` สำหรับ square และปรับ `w ×= 1 + 0.10g` ให้แคบลง
   (เล็บ square จริงไม่ได้กว้างขึ้น แค่ปลายตัดตรง)
2. เพิ่มการ "ตัดมุม" — ที่ `w̄ > 0.8` ให้ `t` ขยับน้อยลง เพื่อให้ได้มุมฉากจริง
   ไม่ใช่ส่วนโค้งที่แบนลงเฉย ๆ
3. ทดลองกับ `Nail_index` (81 verts) เป็นตัวยากที่สุด — ถ้าความละเอียดไม่พอ
   ต้อง subdivide เล็บก่อนสร้าง shape key

**ข้อจำกัดที่ค้นพบ**: `Nail_index` มีเพียง 81 vertices ซึ่งอาจไม่พอสำหรับทรงที่ต้องการ
มุมคม การเพิ่มความละเอียดของเล็บใน pipeline จะเพิ่มสามเหลี่ยมเพียงหลักร้อย
เทียบกับมือ 118,756 tris → **แทบไม่มีต้นทุน ควรทำ**

## 7 · ข้อสรุป

> **R-7 ปิดในเชิงเทคนิค** — สร้างทรงเล็บเป็น morph target ด้วยการดัด geometry
> ตามแกนที่หาด้วย PCA แล้วสลับใน Three.js ได้จริง ทำงานร่วมกับ skinning ได้
> โคนเล็บไม่ขยับ และเพิ่มขนาดไฟล์ไม่ถึง 1%
>
> **ไม่ต้องใช้แผนสำรอง** (สเกลตามแกนยาว) ที่ประเมินไว้ว่าคุณภาพต่ำกว่า
>
> เหลือเพียงการปรับค่าเชิงศิลป์ของ square/squoval ซึ่งเป็นงานปรับพารามิเตอร์
> ไม่ใช่ความเสี่ยงเชิงสถาปัตยกรรม

### สิ่งที่ต้องยกเข้าระบบจริง

| จาก spike | ไปที่ | หมายเหตุ |
|---|---|---|
| `local_frame()` (PCA) | `tools/build_shapes.py` | **แนวคิด** — เขียนใหม่พร้อมเทส |
| `deform()` | เดียวกัน | ปรับค่า square/squoval ก่อน |
| assertion "โคนเล็บขยับ = 0" | เทสของ pipeline | ต้องเป็นเทสอัตโนมัติ |
| การตรวจ `targets` ใน GLB | `tools/verify_model.py` | เพิ่มด่านตรวจว่ามี morph ครบ 4 ต่อเล็บ |
| bug ที่เจอ: ใช้ `geometry.boundingSphere` กับ SkinnedMesh | `docs/algorithms.md` A-09 | **ยืนยันว่าคำเตือนในซอร์สเดิมถูกต้อง** — ผมทำพลาดซ้ำรอยเดิมระหว่าง spike |

### บทเรียนที่ยืนยันซ้ำ

ระหว่าง spike ผมเผลอใช้ `geometry.boundingSphere` เพื่อจ่อกล้องไปที่เล็บ แล้วกล้อง
ไปโผล่ผิดที่ — เป็น**บั๊กเดียวกับที่ `nailViews.ts` ของซอร์สเดิมเขียนคอมเมนต์เตือนไว้**
ว่า geometry ของ SkinnedMesh ค้างอยู่ที่ท่า rest ต้องใช้ `SkinnedMesh.boundingSphere`
ที่คำนวณผ่าน `applyBoneTransform` แทน

→ ยืนยันว่าคอมเมนต์เชิงเหตุผลในซอร์สเดิม **มีค่าจริง** และการตัดสินใจ "ไม่เขียน 3D ใหม่"
ใน `source-audit.md §7` ถูกต้อง
