| | |

| **คำถามที่ต้องตอบ** | ใส่ BVH ให้ mesh มือแล้ว raycast เร็วขึ้นและยังถูกต้องไหม |

## 1 · บทสรุปสำหรับผู้บริหาร

พบ 3 อย่างที่เปลี่ยนแผน:

1. **`three-mesh-bvh` ไม่เร่งความเร็ว `SkinnedMesh` เลย — และไม่มีคำเตือนใด ๆ**
   วิธีติดตั้งมาตรฐาน (`Mesh.prototype.raycast = acceleratedRaycast`) **ไม่มีผล**
   เพราะ `THREE.SkinnedMesh.prototype` มีเมธอด `raycast` เป็นของตัวเองที่บดบังของแม่
2. **การ raycast มือแบบปัจจุบันช้าถึง 113 มิลลิวินาทีต่อรังสีเดียว** — ใช้งานเชิงโต้ตอบไม่ได้
3. **ทางแก้ที่ถูกต้องคือ bake ตำแหน่งที่ผ่านการ skin แล้วสร้าง static Mesh + BVH**
   → 7.5 ไมโครวินาทีต่อรังสี **เร็วขึ้น 15,104 เท่า และถูกต้อง 100%**

## 4 · ทำไม B และ C จึงไม่ได้พิสูจน์อะไร

เฟส B "เร็วขึ้น 1.2 เท่า" ไม่ใช่ผลของ BVH แต่เป็นความแปรปรวนระหว่างรอบ
และเฟส C ที่ได้ความถูกต้อง 100% ทั้งที่ควรผิด — **เพราะ BVH ไม่เคยถูกเรียกใช้เลย**

### หลักฐานเชิงกลไก

ตรวจ prototype ของ three.js โดยตรง:

```js
Object.getOwnPropertyNames(THREE.SkinnedMesh.prototype)
// → ['constructor', 'computeBoundingBox', 'computeBoundingSphere', 'copy',
//    'raycast', 'getVertexPosition', 'bind', 'pose', ...]

Object.prototype.hasOwnProperty.call(THREE.SkinnedMesh.prototype, 'raycast')  // → true
```

`SkinnedMesh` **override `raycast` เป็นของตัวเอง** ดังนั้นการทำตามคู่มือของ three-mesh-bvh

```js
THREE.Mesh.prototype.raycast = acceleratedRaycast
```

จึงถูกบดบังทั้งหมดสำหรับ `SkinnedMesh` — **เงียบสนิท ไม่มี warning ไม่มี error**
ผู้พัฒนาจะเชื่อว่า BVH ทำงานอยู่ทั้งที่ไม่ได้ทำงานเลย

ส่วน `acceleratedRaycast` และ `MeshBVH.raycastObject3D` เองไม่มีการ์ดกัน SkinnedMesh
(ตรวจซอร์สแล้ว) — ถ้าถูกเรียกมันจะใช้ BVH ทันที ซึ่งนำไปสู่เฟส F

---

## 5 · เฟส F — ทางลัดที่ดูเหมือนถูกแต่ผิด

เมื่อรู้สาเหตุแล้ว สิ่งแรกที่ทุกคนจะทำคือแพตช์ `SkinnedMesh.prototype.raycast` ด้วย

```js
THREE.SkinnedMesh.prototype.raycast = acceleratedRaycast   // ❌ อย่าทำ
```

**ผล: เร็วขึ้น 45,313 เท่า แต่ถูกต้องเพียง 22.5%** (9 จาก 40 รังสี)

เพราะ BVH ถูกสร้างจาก `geometry.attributes.position` ซึ่งเป็น **ท่า rest**
ส่วนมือจริงถูกบอร์นดัดไปแล้ว → รังสีชนสามเหลี่ยมที่ "เคยอยู่ตรงนั้น" ไม่ใช่ที่อยู่จริง

ในบริบทของแอปนี้แปลว่า **สีจะไปลงผิดตำแหน่งทันทีที่ผู้ใช้ขยับสไลเดอร์สัดส่วนมือ**
และจะผิดแบบเงียบ ๆ ไม่มี error ให้จับ

> เฟสนี้มีไว้เพื่อบันทึกหลักฐาน ไม่ใช่แค่เขียนว่า "อย่าทำ" — เพราะทางลัดนี้
> น่าดึงดูดมาก (เร็วกว่าทางที่ถูกต้องอีก 3 เท่า) และคนที่ไม่ได้วัดความถูกต้องจะเลือกมัน

## 6 · ทางแก้ที่ถูกต้อง — Baked Raycast Proxy

```
เมื่อท่าบอร์นเปลี่ยน (ผู้ใช้ปล่อยสไลเดอร์สัดส่วน):
  1. เดินทุก vertex ของ mesh มือ เรียก applyBoneTransform → Float32Array ใหม่   [22.6 ms]
  2. สร้าง BufferGeometry ใหม่จากตำแหน่งที่ bake แล้ว (ใช้ index เดิมร่วมกัน)
  3. สร้าง MeshBVH จาก geometry นั้น                                          [32.2 ms]
  4. ใส่ใน Mesh ธรรมดา (ไม่ใช่ SkinnedMesh) ที่ matrixWorld เท่ากับมือ
  5. ใช้ Mesh ตัวนี้เป็น occluder ในการ raycast แทน mesh มือจริง
     — ไม่ใส่ใน scene ไม่เรนเดอร์ ใช้เพื่อการยิงรังสีอย่างเดียว
```

| ข้อดี | ข้อเสีย |
|---|---|
| เร็วขึ้น **15,104 เท่า** (113 ms → 7.5 µs) | ต้นทุน 54.8 ms ต่อการเปลี่ยนท่า |
| **ถูกต้อง 100%** | ใช้หน่วยความจำเพิ่ม: BVH 1.04 MB + position buffer ~0.77 MB |
| ไม่ต้องแพตช์ prototype ของ three.js | ต้องจัดการวงจรชีวิตของ proxy เอง |
| ทดสอบได้ (เป็น Mesh ธรรมดา) | ต้องระวังไม่ให้ proxy หลุดจากท่าจริง |

**54.8 ms ยอมรับได้ไหม** — สไลเดอร์สัดส่วนถูกลากแล้วปล่อย ถ้า debounce ให้ rebuild
เฉพาะตอนปล่อย จะเกิดการหยุด 54.8 ms หนึ่งครั้ง ซึ่งผู้ใช้แทบไม่รู้สึก
ถ้าต้องการให้ลื่นระหว่างลากด้วย ให้ย้ายไป Web Worker (มีแผนไว้แล้วใน `optimization/bvhWorker.ts`)

## 7 · ผลกระทบต่อซอร์สเดิม (สำคัญ)

`PaintController.tsx:49` ของ `NailDesine-TEST` ยิงรังสีใส่ `[...visibleNails(), ...occluders]`
ทุก `pointermove` โดย `occluders` มี mesh มือ 118,756 tris อยู่ด้วย และ **ไม่มี BVH**

three.js `Raycaster.intersectObjects` **ไม่มี early-out** — มันทดสอบทุกวัตถุในรายการ
แล้วค่อยเรียงตามระยะ ดังนั้น mesh มือถูกไล่ทุกสามเหลี่ยมทุกครั้งเสมอ

→ **การลากเส้นในซอร์สเดิมน่าจะมี latency ระดับ 100 มิลลิวินาทีต่อการขยับนิ้วหนึ่งครั้ง**

ข้อสังเกตนี้ยกระดับ **TD-2** จาก "ยังไม่ได้วัด" เป็นปัญหาที่วัดแล้ว และอธิบายว่าทำไม
`textures.ts` ถึงต้องมีกลไก `defaultScheduler` ที่รวบงานให้เหลือรอบเดียวต่อเฟรม —
เป็นการแก้อาการปลายทาง ไม่ใช่แก้ที่ต้นเหตุ

> **ข้อจำกัดของข้อสรุปนี้**: ผมวัดจากฉากทดสอบของ spike ไม่ใช่จากการใช้งานจริงของแอปเดิม
> รูปแบบรังสีอาจต่างกัน ต้องยืนยันซ้ำด้วยการวัดในแอปจริงที่ Slice 2

## 9 · ข้อสรุป

> **R-4 ปิดแล้ว** แต่คำตอบตรงข้ามกับที่ออกแบบไว้ใน D-06
>
> `three-mesh-bvh` **ใช้กับ SkinnedMesh โดยตรงไม่ได้** และความล้มเหลวนั้น **เงียบสนิท**
> ทางแก้คือ **bake ตำแหน่งที่ผ่านการ skin แล้วสร้าง static proxy + BVH**
> ซึ่งให้ผลเร็วขึ้น 15,104 เท่าโดยยังถูกต้อง 100%
>
> ถ้าไม่ได้ทำ spike นี้ เราจะใส่ BVH ตามคู่มือ เห็นว่า "ไม่ error" แล้วเชื่อว่าใช้ได้
> จนกระทั่งไปวัดตอน Slice 8 แล้วพบว่าไม่เร็วขึ้นเลย — หรือแย่กว่านั้นคือแพตช์
> `SkinnedMesh.prototype` แล้วได้ระบบที่เร็วแต่ทาสีผิดตำแหน่งโดยไม่มีใครสังเกต

### บทเรียนเชิงวิธีการ

**การวัดความเร็วอย่างเดียวไม่พอ ต้องวัดความถูกต้องคู่กันเสมอ** —
เฟส F เร็วกว่าเฟส D ถึง 3 เท่า ถ้า benchmark วัดแค่เวลา เราจะเลือกทางที่ผิด
ทุก benchmark ของโครงงานนี้ต้องมีคอลัมน์ "ตรงกับความจริงกี่เปอร์เซ็นต์" ควบคู่เสมอ
